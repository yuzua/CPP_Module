# ex05 Design Review — Harl 2.0

`architecture.md` の設計と subject 要件に対して、現在の実装（`Harl.hpp` / `Harl.cpp` / `main.cpp` / `Makefile` / `tests/`）をレビューした記録。

**検証条件**: 本レビューは**静的レビューのみ**。この環境ではシェルが応答を返さないため、`make` / `make test` の実行結果は未取得。「ビルドが通る」「テストが通る」は未検証事項として扱う。

---

## 1. 総合判定

| 観点 | 判定 | 要約 |
|------|------|------|
| subject 要件充足 | **ほぼ充足** | クラス構成・private 4関数・メンバ関数ポインタ dispatch・if の森回避は達成 |
| Problem Framing | **ready** | 解くべきことと手段が一致 |
| Domain Model | **sufficient** | 閉じた4レベル、状態なし、情報隠蔽が目的として成立 |
| Design by Contract | **conditional** | 契約自体は妥当だが、**テストで検証できている契約が少ない** |
| Interface / Implementation | **separated** | 公開面は `complain` のみ。文言と表は `.cpp` に閉じている |
| 性能 | **問題なし（改善余地あり）** | dispatch は誤差。ただし呼び出しごとの表再構築は不要なコスト |
| ビルド | **軽微な不備** | ヘッダ依存が Makefile に無い |

**結論**: 提出可能な水準に達している。優先度が高い改善は **テスト網（H-3, H-4）** と **表の持ち方（H-1）** の3点。

## 3. 妥当な点（変更不要）

### 3.1 dispatch の骨格

メンバ関数ポインタの取り扱いは正しい。`&Harl::debug` でアドレスを取り、`(this->*funcs[i])()` で `this` に束縛して呼ぶという形になっており、subject が要求する学習内容を満たしている。レベル判定が「ループ内の単一 `if`」に収まっているため、`else if` の鎖という禁止形にも該当しない。

### 3.2 情報隠蔽

4つの文言関数が private で、公開面が `complain` 1本に絞られている。`main.cpp` に英文が一切なく、文言は `Harl.cpp` の中だけにある。これは ex04 で「状態が無いならクラスにしない」と判断したのとは別の目的（情報隠蔽）でクラスが機能している状態であり、設計として一貫している。

### 3.3 テスト oracle を汚さない構成

コンストラクタとデストラクタが空で、何も出力しない。出力全文を比較するテストに移行するときに、そのまま golden file を作れる状態になっている。

### 3.4 ビルド設定

`-Wall -Wextra -Werror -std=c++98` が入っており、`SRCS` も正しい。`test` ターゲットがあるのも設計どおり。

## 4. 指摘事項

### H-1（中）表が呼び出しごとに再構築され、件数が3箇所に散っている

**場所**: `Harl.cpp` の `complain`

```cpp
void (Harl::*funcs[4])(void) = {...};
std::string const levels[4] = {"DEBUG", "INFO", "WARNING", "ERROR"};
for (int i = 0; i < 4; i++)
```

**問題は2つある。**

1. **保守性（主）**: レベル名と関数の対応が2本の配列に分かれ、**添字が一致していることだけ**が対応の根拠になっている。さらに `4` が3箇所（配列2つとループ条件）に現れる。レベルを1つ増やすとき、4箇所を同時に正しく直す必要があり、片方だけ直すと「INFO を渡すと warning が出る」類のズレが静かに入る。`architecture.md` の不変条件 I-01（表は4レベルをちょうど1回ずつ含む）と I-02（名前と handler が一致）を、コード構造が支えていない。

2. **性能（従）**: どちらの配列も `static` ではないため、`complain` を呼ぶたびに 4本のメンバ関数ポインタを書き、**`std::string` のコンストラクタを4回**（対応するデストラクタも4回）実行している。インデックスアクセスそのものより、この per-call 構築のほうが大きい。

**推奨**: 対応を1行に持つ表へ変更し、件数を `sizeof` から算出する。

```cpp
typedef void (Harl::*ComplaintHandler)(void);
struct Entry {
    const char *level;
    ComplaintHandler handler;
};

static const Entry table[] = {
    {"DEBUG",   &Harl::debug},
    {"INFO",    &Harl::info},
    {"WARNING", &Harl::warning},
    {"ERROR",   &Harl::error}
};
const std::size_t count = sizeof(table) / sizeof(table[0]);
```

`const char *` と `static` にすることで、表は起動時に読み取り専用領域へ置かれ、**実行時の初期化がゼロ**になる。レベル追加は「private メソッド1つ + 表1行」で済み、件数の修正も不要になる。

### H-2（中）未知レベルの扱いがコード上も無記述

**場所**: `complain` のループ末尾

一致しなければ何もせずに関数を抜ける実装になっている。これは `architecture.md` の決定（無出力・正常終了）と一致しているが、**コードにその意図が書かれていない**ため、「実装漏れ」と「意図した無出力」を読み手が区別できない。subject が未知レベルの挙動を指定していないだけに、defense で必ず問われる箇所。

**推奨**: ループ末尾に意図を示す短いコメントを1行だけ置く。加えて H-4 のテストで挙動を固定する。

---

### H-3（中）テストが「含む」判定のみで、契約の主要部分を検証できていない

**場所**: `tests/run_tests.sh`

現状は `./harl` を1回実行した出力に対して、`[ DEBUG ]` などの見出し4つと `manager now.` の5箇所を部分一致で確認している。この形では次が検証できない。

| 検証できないこと | 理由 |
|------------------|------|
| **排他性**（C-04: 1レベル呼び出しで他レベルの文言が出ない） | 部分一致なので、余計な出力が増えても PASS になる |
| **順序と回数**（T-09） | 出現位置・回数を見ていない |
| **本文の一致** | DEBUG / INFO / WARNING の**本文が未検証**（見出しのみ）。ERROR だけ本文の一部を見ている |
| **未知レベルで何も出ないこと**（C-03） | そもそも `main` が未知レベルを呼んでいない |
| 終了コード | `./harl` の exit status を確認していない |

**推奨**: 出力全文を golden file と `diff` する方式へ切り替える。

```bash
"$BIN" > "$ROOT/tests/actual.txt"
diff -u "$ROOT/tests/expected_output.txt" "$ROOT/tests/actual.txt"
```

これ1つで、本文・順序・回数・排他性・未知レベルでの無出力がまとめて検証できる。golden file は初回に実行結果を目視確認してから固定する。`fclean` に `tests/actual.txt` の削除を足しておく。

---

### H-4（中）`main.cpp` が既知4レベル1周のみ

**場所**: `main.cpp`

subject は「Harl がよく文句を言うことを示すテスト」を求めているが、現状は4レベルを1回ずつ呼ぶだけで、異常系が一切ない。

**推奨**: 次を追加する（設計書 T-06〜T-09 に対応）。

| 呼び出し | 期待 |
|----------|------|
| `complain("NOPE")` | 無出力 |
| `complain("")` | 無出力 |
| `complain("debug")` | 無出力（大小区別の明文化） |
| 4レベルをもう1周 | 同じ出力が繰り返される |

未知レベルは「出力が無いこと」が oracle なので、`std::cout << "--- unknown ---" << std::endl;` のような区切り行を挟むと、`diff` で位置が特定しやすくなる。区切り行はテスト都合の出力なので、`main.cpp` 側に置く（`Harl` に入れない）。

---

### H-5（小）Makefile にヘッダ依存がない

**場所**: `Makefile`

`$(OBJS)` が `Harl.hpp` に依存していないため、**ヘッダだけを編集したときに再ビルドされない**。宣言と定義が食い違ったまま古いオブジェクトがリンクされ、原因の分かりにくい挙動につながる。

**推奨**: 1行足す。

```makefile
$(OBJS): Harl.hpp
```

---

### H-6（小）`complain` のシグネチャが subject 文言と異なる

**場所**: `Harl.hpp`

subject は `void complain( std::string level );`（値渡し）、実装は `std::string const &`。Module 01 の主題が参照であることを踏まえれば妥当な選択で、通例この差異は問題にならない。ただし**意図的な選択であることを説明できる状態**にしておく必要がある。

**推奨**: 現状維持。defense では「コピーを避け、呼び出し側の一時オブジェクトも受けられる `const &` にした。要件の意味（レベル名を受け取る）は変えていない」と説明する。評価者が subject 文言の厳守を求めた場合のみ値渡しへ戻す。

---

### H-7（小）1回の `complain` で `std::endl` を2回使っている

**場所**: 各 handler

見出し行と本文行でそれぞれ `std::endl` を使っているため、**フラッシュが2回**走る。ex05 の規模では実害はないが、「dispatch の速さより I/O のほうが支配的」という事実の裏返しでもあり、出力側のほうが最適化余地が大きいことを示す例になっている。

**推奨**: 必須ではない。揃えるなら見出し側を `"[ DEBUG ]\n"` にして、行末だけ `std::endl` にする。**この変更は出力バイト列を変えない**ので golden file はそのまま使える。

---

### H-8（情報）`const` メンバ関数にするかの判断

4つの handler も `complain` もオブジェクトの状態を変更しないため、const 正しさの観点では `void debug(void) const;` にできる。その場合、ポインタ型も `void (Harl::*)(void) const` になる。

一方で subject はシグネチャを `void debug( void );` と明記しており、評価シートで宣言の一致を見られる可能性がある。**現状維持を推奨**し、defense で「状態を変更しないので const にもできるが、subject の宣言に合わせた」と言えるようにしておくのが安全。

---

### H-9（情報）WARNING の文言が subject 例と微差

実装は `...you started working here since last month.`、subject 例は `...just last month.`。subject は「自分のコメントを使ってもよい」と明記しているため**問題なし**。意図的な自作文言であることを `architecture.md` 側に一言残しておくと、指摘されたときに即答できる。

---

### H-10（情報）コピー制御は未定義

`Harl` はメンバ変数を持たないため、暗黙のコピーコンストラクタ・代入演算子で問題は起きない。Orthodox Canonical Form は Module 02 の主題であり、ex05 で書く必要はない。

---

## 5. 契約カバレッジ

`architecture.md` の契約項目に対する検証手段の内訳。

| 契約 | 内容 | 検証手段 |
|------|------|----------|
| C-01 | Pre なし（全域関数） | コードレビュー（引数検査なし＝意図どおり） |
| C-02 | 既知レベル → 対応文言が1回 | **自動テスト（見出しのみ）**。本文は ERROR だけ |
| C-03 | 未知レベル → 無出力 | **未検証** |
| C-04 | 他レベルの文言が混ざらない | **未検証** |
| C-05 | 表 + メンバ関数ポインタで dispatch | コードレビュー |
| C-06 | 副作用は stdout のみ、状態不変 | コードレビュー（メンバ変数なし） |
| C-07 | 同じレベル → 同じ文言 | **未検証**（2周テストで確認可能） |
| C-08 | handler は固定文言を1回出力 | **自動テスト（部分）** |
| C-09 | handler は private。外部から呼べない | **未検証**（コンパイルエラーの確認をしていない） |

自動テストで検証できている契約は **9件中 2件（部分的）**。H-3 の golden diff と H-4 の呼び出し追加で、C-02・C-03・C-04・C-07・C-08 が一度にカバーできる。C-09 は `main.cpp` にコメントアウトした `// harl.debug();` を置き、defense で「これを外すとコンパイルエラーになる」と示すのが簡便。

## 6. 性能の観点（結論: 現状で問題なし）

| 要素 | 1回の `complain` あたり | 評価 |
|------|------------------------|------|
| インデックスアクセス `funcs[i]` | オフセット加算1〜2命令 | 誤差 |
| 文字列比較（最大4回） | `strlen` 相当 + `memcmp` | `if/else` の森と**同じ仕事** |
| メンバ関数ポインタ経由の呼び出し | 間接呼び出し1回（インライン化されない） | 数ナノ秒オーダー |
| **`std::string` 構築4回（現状）** | コンストラクタ/デストラクタ各4回 | **H-1 で消せる不要コスト** |
| `std::endl` × 2 | フラッシュ2回（`write` システムコール） | **ここが支配的**（マイクロ秒オーダー） |

dispatch の最適化に意味はなく、削るなら I/O 側。そして H-1 の修正は「わかりやすさ」と「per-call コスト削減」が同時に得られるため、トレードオフではない。

要素数4の線形走査は `std::map` より速いのが通例であり、`std::map` への置き換えは**性能面でも不利**。

## 7. 保守性・拡張性

| シナリオ | 現状のコスト | H-1 適用後 |
|----------|--------------|------------|
| レベル追加（例 `FATAL`） | private メソッド1つ + **4箇所の修正**（配列2つ・件数・ループ） | private メソッド1つ + **表1行** |
| 文言変更 | `Harl.cpp` のみ | 同じ |
| 出力書式変更 | `Harl.cpp` + テスト oracle | 同じ |
| **ex06 の filter**（指定レベル以上を連続出力） | 並行配列でも index は取れるが対応が追いにくい | 表の並び＝重大度順なので、一致 index 以降を回すだけ |

`main.cpp` と `complain` の呼び出し側がレベル追加の影響を受けないという点は、現状でも達成できている。

## 9. Defense 想定問答

| 質問 | 回答の骨子 |
|------|------------|
| なぜクラスにしたのか | subject 要件に加え、4つの文言関数を private に閉じて入口を `complain` 1本に絞るため（情報隠蔽）。状態を守るためではない |
| `if` が1つあるが森ではないのか | ループ内の単一比較であり、レベルが増えても分岐の数は増えない。増えるのは表の行だけ |
| メンバ関数ポインタの文法 | `&Harl::debug` は `this` を含まないアドレス。`(this->*p)()` で対象オブジェクトに束縛して呼ぶ |
| 未知レベルはどうなるか | 無出力で正常終了。subject 未指定なので設計判断として固定し、テストで挙動を確認している（H-4 適用後） |
| `complain` が `const &` な理由 | コピー回避。要件の意味は変えていない |
| 性能は気にしたか | dispatch は出力コストに比べ誤差。表を `static` にして per-call の `std::string` 構築を避けるのが唯一意味のある改善 |
| ex06 へどうつながるか | 表の並びが重大度順なので、一致位置以降を回せば filter になる |
