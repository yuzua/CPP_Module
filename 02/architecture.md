## 1. 設計の進め方 — mino skill suite の当て方

参照: [inspired-mino-design-skills](https://github.com/my-take-dev/inspired-mino-design-skills)（ミノ駆動氏の公開資料を基にした非公式 Skill 集）

この Skill 集は「AI が毎回同じコードを書くこと」ではなく、
**違う実装でも同じ問題・契約・モデル整合・公開境界を満たせること**を再現性と定義している。
7 つの Skill のうち、今回の課題規模で意味があるのは次の 5 つ。

| Skill | 何をする | 本モジュールでの適用 |
|-------|---------|---------------------|
| `mino-problem-framing` | 技術案を「候補手段」に戻し、問題・目的・成功条件・拒否条件に分ける | 「Fixed クラスを作れ」を「**何を保証する数値型か**」に翻訳（→ 2章） |
| `mino-domain-model-completeness` | 概念・値制約・状態・失敗・writer/reader の欠落を監査 | 値域・分解能・丸め・オーバーフロー・0除算の**漏れ探し**（→ 各 ex の「モデル欠落」表） |
| `mino-design-by-contract` | 要件を 事前条件 / 事後条件 / 不変条件 / 失敗保証 / 契約テスト に変換 | 各演算子の契約表とテスト ID（→ 各 ex の「公開契約」「テスト項目」） |
| `mino-interface-implementation-separation` | 利用者が知るべき事と内部実装を分ける | `.hpp` に何を置き `.cpp` に何を隠すか、`_value` を外に漏らさない設計 |
| `mino-architecture-quality-strategy` | 品質の優先順位と trade-off を product value から決める | 「**精度 vs 値域 vs 単純さ**」の優先順位を先に固定（→ 3.3） |

`mino-reproducible-development`（複数成果物の統合ルータ）と `mino-core`（内部基盤）は、
単一クラス・単一バイナリの本課題では**過剰**なので使わない。
Skill 集自身も「小規模・単一成果物には統合 Skill を起動しない」と明記している。

### 1.1 Skill 集から借りた「判断の型」

本書の各 ex は、次の順で書いてある。これはそのまま **defense での説明順**に使える。

```text
  ① 問題（何を保証する？）        ← problem-framing
  ② モデル（概念・値制約・失敗）   ← domain-model-completeness
  ③ 契約（pre / post / invariant）← design-by-contract
  ④ 境界（hpp に何を出す？）      ← interface-implementation-separation
  ⑤ 設計判断（案A/B/C と推奨）
  ⑥ テスト項目（契約に紐づく）
```

また Skill 集の Hard Gate を、この課題向けに読み替えた**自分ルール**を置く。

| Skill の Hard Gate | 本課題での読み替え |
|--------------------|-------------------|
| 「if 数・interface 数を品質と扱わない」 | 演算子を全部生で書くのが偉いのではない。`<` と `==` から残りを導く方が壊れにくい |
| 「N/A は理由と根拠、unknown は確認方法を持つ」 | 「オーバーフロー時は未定義」と書くなら、**なぜ未定義でよいか**も書く（subject が許容しているから） |
| 「表が埋まったことを model complete としない」 | 演算子が全部コンパイルを通ったことを「完成」としない。**負数・境界値**を通して初めて完成 |
| 「最終的な価値判断・公開契約は人間が持つ」 | 丸め方（floor か 0 方向か）は**自分で決めて文書化**する。どちらも正解 |

## 2. 前提知識 — 固定小数点数とは何か

### 2.1 int と float の対立（subject が記事を読ませる理由）

| | `int` | `float`（IEEE 754 単精度） |
|---|---|---|
| 表せるもの | 整数のみ | 小数も表せる |
| 精度 | **完全に正確**（範囲内なら） | 近似。`0.1f` は正確に 0.1 ではない |
| 分解能 | どこでも 1 | 値が大きいほど**粗くなる**（指数部が動くため） |
| 速度 | 速い | FPU 依存。組込みでは遅い／無い場合も |
| 罠 | 桁あふれ | `a + b - b != a`、`==` 比較が危険、NaN / Inf |

`float` は「**小数点の位置が動く**（floating = 浮動）」から、値が大きいと小数部を捨てる。
たとえば `16777217.0f` は表現できず `16777216.0f` になる。

### 2.2 固定小数点数（fixed point）の考え方

**小数点の位置を固定してしまえばいい。** それだけ。

整数 `_value` を持ち、「この整数は本当は \(2^8 = 256\) 倍されている」と**約束**する。

```text
  実数値  =  _value / 256

  _value = 256   →   1.0
  _value = 128   →   0.5
  _value = 1     →   0.00390625   ← 表せる最小の刻み（ε）
  _value = 2586  →   10.1015625
```

ビットで見るとこうなっている（これを **Q23.8 形式** と呼ぶ）。

```text
   int _value (32bit)
  ┌─┬───────────────────────┬─────────┐
  │S│    整数部 23bit        │小数部 8bit│
  └─┴───────────────────────┴─────────┘
    ↑                        ↑
   符号            ここに小数点が「固定」されている
```

| 性質 | Q23.8（`int` + 8bit） の場合 |
|------|------------------------------|
| **分解能**（刻み幅） | 常に \(1/256 = 0.00390625\)。大きい値でも粗くならない |
| **値域** | \(-8388608.0\) 〜 \(+8388607.99609375\) |
| **加減算** | ただの `int` の加減算。**誤差ゼロ**・高速 |
| **乗除算** | スケール調整（シフト）が要る。中間でオーバーフローしやすい |
| **弱点** | 値域が狭い。`float` のような広いダイナミックレンジは無い |

> **ε（イプシロン）の意味**: subject の「\(1 + \epsilon > 1\) となる最小の \(\epsilon\)」とは
> **`_value` を 1 増やすこと** = `0.00390625`。ex02 の `++` の答えはこれ。

### 2.3 Problem Frame（problem-framing の適用）

技術語（「Fixed クラス」「演算子オーバーロード」）を外して問題を書くと、こうなる。

| 項目 | 内容 |
|------|------|
| **観測** | C++ の組込み型は「正確だが整数のみ」か「小数を扱えるが不正確」の二択しかない |
| **誰の何が困る** | グラフィクス・音声・科学計算の書き手が、**一定の刻み幅**と**予測可能な誤差**を必要としている |
| **目的** | 「刻み幅が常に一定で、加減算が厳密な小数型」を C++ に持ち込む |
| **成功条件** | ① 小数を保持できる ② `int`/`float` と相互変換できる ③ 組込み型と同じ記法（`a + b`, `a < b`, `std::cout << a`）で書ける ④ `int` と同じくコピー・代入が安全 |
| **拒否条件** | 値域を超えた入力を「なんとなく丸める」等の黙った救済はしない。0 除算も救わない（subject が明示的に許容） |
| **候補手段（= 技術）** | `int` + 固定スケール（採用）／`long` 化／有理数クラス／`double` ラッパ |
| **未決（人間が決める）** | `toInt()` の丸め方向、乗算の中間型、`explicit` を付けるか |

**ポイント**: 「クラスを作れ」は手段。**問題は「一定分解能の数値型が無い」こと**。
defense でこう言えると、丸暗記していないことが伝わる。

## 3. モジュール全体の方針

### 3.1 D-00: ex 間でのファイル運用

42 は「各 ex ディレクトリに必要ファイルを実体で置く」ことを要求する。共通化はできない。

| 案 | 内容 | メリット | デメリット |
|----|------|---------|-----------|
| **A: 段階的コピー**（推奨） | ex00 完成 → ex01 にコピーして追記 → ex02 → ex03 | 各 ex が subject の要求ちょうどになる。差分で成長が見える | コピー漏れ・ログ方針の直し忘れ |
| B: 最初に ex03 相当を作って削る | 手戻りが少ない | **ex00 に未要求の機能が入る**と「subject を読んでいない」と見られる。減点対象 |
| C: symlink / include で共有 | DRY | 提出規則違反のリスク。clone 環境で壊れる |

**推奨: 案A。** ただし**コピー直後に必ずやること**を決めておく。

```text
ex00 → ex01 コピー後:  getRawBits/setRawBits のログを消す（3.2 参照）
ex01 → ex02 コピー後:  main.cpp を捨てて書き直す（前の main は残さない）
ex02 → ex03 コピー後:  Fixed はそのまま。Point / bsp を足すだけ
```

### 3.2 D-01: ログ（コンストラクタ等のメッセージ）方針 ★重要

subject の期待出力を素直に読むと、**ex ごとにログの方針が違う**。ここを外すと評価で揉める。

| メッセージ | ex00 | ex01 | ex02 | ex03 |
|-----------|------|------|------|------|
| `Default constructor called` | **出す** | 出す | 出す（例では省略と明記） | 出す |
| `Copy constructor called` | **出す** | 出す | 出す | 出す |
| `Copy assignment operator called` | **出す** | 出す | 出す | 出す |
| `Destructor called` | **出す** | 出す | 出す | 出す |
| `Int constructor called` | — | **出す** | 出す | 出す |
| `Float constructor called` | — | **出す** | 出す | 出す |
| `getRawBits member function called` | **出す** | **出さない** ★ | 出さない | 出さない |

★ の根拠: ex01 の期待出力には `Copy assignment operator called` があるのに
`getRawBits member function called` が**一度も無い**。
つまり ex01 以降のリファレンス実装は、`getRawBits` のログを消している（または `operator=` が `getRawBits` を経由していない）。

> **時間節約の裏技**: ログ文字列を `Fixed.cpp` の先頭に集めておくと、ex を進めるとき消す場所が一箇所になる。

### 3.3 品質の優先順位（architecture-quality-strategy の適用）

すべての品質を最大化しない。**先に順位を決めて、defense でそう言う。**

| 順位 | 品質 | 理由 | 犠牲にするもの |
|------|------|------|---------------|
| 1（primary） | **仕様適合**（subject の期待出力に一致） | 評価の合否そのもの | — |
| 2（primary） | **説明可能性**（自分で全行説明できる） | AI 章が示す評価基準 | 巧妙なテンプレ技法 |
| 3（secondary） | **数値的正しさ**（加減算が厳密、負数も正しい） | 「動くが負数で壊れる」は defense で必ず突かれる | 若干の記述量 |
| 4（constraint） | **C++98 準拠**・`-Wall -Wextra -Werror` | 制約。妥協不可 | `long long`, `auto`, `constexpr` |
| 5（intentionally not optimized） | **値域の広さ / 速度** | 課題の主題ではない | オーバーフローは未定義のまま放置してよい（**ただし説明はできること**） |

## 4. ex00 — 正統的正準形式での最初のクラス

### 4.1 要件（subject）

| 種別 | 内容 |
|------|------|
| 提出 | `Makefile`, `main.cpp`, `Fixed.hpp`, `Fixed.cpp` |
| private | `int` の値、`static const int` の小数部ビット数（**整数リテラル 8**） |
| public | デフォルトコンストラクタ（値 0）、コピーコンストラクタ、コピー代入演算子、デストラクタ |
| public | `int getRawBits(void) const;` / `void setRawBits(int const raw);` |

### 4.2 OCF（正統的正準形式）とは — なぜ 4 つ必要か

C++ は、書かなければ**コンパイラが勝手に 4 つを作る**（暗黙生成）。
暗黙版は「メンバを 1 個ずつコピーする」だけ（**シャローコピー**）。

`Fixed` は `int` しか持たないので暗黙版でも正しく動く。**ではなぜ書くのか。**

```cpp
class Bad {
    char *buf;          // new[] で確保したメモリ
};
Bad a;
Bad b = a;              // 暗黙のコピーコンストラクタ → buf の「アドレス」をコピー
                        // → a と b が同じメモリを指す
                        // → 両方のデストラクタが delete[] → 二重解放でクラッシュ
```

| 理由 | 説明 |
|------|------|
| **習慣づけ** | Module 03 以降、ポインタを持つクラスが出た瞬間に必須になる。先に手を慣らす |
| **観測可能にする** | ログを出すことで「**いつコピーが起きているか**」が目に見える。これが ex00 の本当の教材 |
| **意図の明示** | 「コピーしてよい型である」ことをコードで宣言する |

> 3 つ（コピーコンストラクタ / コピー代入 / デストラクタ）のどれか 1 つを書いたら残り 2 つも書け、
> というのが **Rule of Three**。OCF はそれにデフォルトコンストラクタを足したもの。

### 4.3 モデル（domain-model-completeness の適用）

| 観点 | 内容 | 欠落していないか |
|------|------|-----------------|
| 概念 | 固定小数点数 = `raw` と `scale(=2^8)` の組 | ✓ |
| 値制約 | `raw` は `int` の全域。**`_fractionalBits` は常に 8**（不変条件） | ✓ |
| 状態 | 状態遷移なし。**値オブジェクト**（不変ではないが、状態機械ではない） | ✓ |
| writer | デフォルトコンストラクタ / コピーコンストラクタ / `operator=` / `setRawBits` の **4 経路** | ✓ 全経路が `_value` を一貫して扱うか確認 |
| reader | `getRawBits` のみ | ✓ |
| 失敗 | ex00 には失敗が無い（`setRawBits` は任意の `int` を受ける） | ✓ N/A（理由: 全 `int` が有効な raw だから） |
| 時間 | 関係なし | N/A |

**この表の使い方**: 「`_value` を書き換えられる経路は 4 つ」と分かっているから、
**ex01 以降で経路が増えたとき（int/float コンストラクタ）に、そこも同じ不変条件を守るか**を確認できる。

### 4.4 設計判断

#### D-02: `_fractionalBits` の置き場所

| 案 | 書き方 | メリット | デメリット |
|----|-------|---------|-----------|
| A | `.hpp` に `static const int _fractionalBits = 8;` のみ | 1 行。ヘッダを見れば 8 と分かる。定数式として使える | **odr-used** されると**リンクエラー**（例: `const int&` で受ける関数に渡したとき） |
| B | `.hpp` で宣言、`.cpp` で `const int Fixed::_fractionalBits = 8;` | リンクエラーにならない | ヘッダだけ見ても値が分からない。配列サイズ等の定数式に使えない |
| **C（推奨）** | **両方**: ヘッダで `= 8` 初期化 + `.cpp` に定義（初期化子なし） | A と B の利点を両取り。C++98 の正式な書き方 | 2 箇所に書くので少し冗長 |

```cpp
// Fixed.hpp
class Fixed {
private:
    int                 _value;
    static const int    _fractionalBits = 8;   // ← クラス内初期化（整数型のみ可）
};

// Fixed.cpp
const int Fixed::_fractionalBits;              // ← 定義（初期化子は書かない。書くと二重初期化でエラー）
```

> **static メンバとは**: インスタンスごとではなく、**クラスに 1 個だけ**存在するデータ。
> `Fixed a, b;` を作っても `_fractionalBits` は 1 個。だから `sizeof(Fixed) == sizeof(int)` のまま。

#### D-03: コピーコンストラクタの実装方針 ★

subject の期待出力に `// <-- This line may be missing depending on your implementation` があるのはここ。

| 案 | 実装 | ex00 の出力 | メリット | デメリット |
|----|------|-----------|---------|-----------|
| **A（ex00 推奨）** | `Fixed(Fixed const &o) { *this = o; }` | `Copy constructor called` → `Copy assignment operator called` → `getRawBits ...` | **subject の期待出力と完全一致**。コピー処理が `operator=` の 1 箇所に集約（DRY） | `_value` を一度デフォルト初期化してから代入する 2 度手間。実務では非効率 |
| B | `Fixed(Fixed const &o) : _value(o._value) {}` | `Copy constructor called` のみ | 初期化リストで一発。**正統的で高速**。const メンバがあっても書ける | subject の例より 1〜2 行少ない（subject は許容と明記） |

**推奨: ex00・ex01 は案A、ex03 は案B。**

**ex01 も案A でなければ期待出力に一致しない**（実機で検証済み）。ex01 の期待出力を数えると、
`Fixed const d( b );` の直後に `Copy constructor called` と `Copy assignment operator called` の
**2 行**が並んでいる。案B なら 1 行しか出ないので、`Copy assignment operator called` が 1 つ足りなくなる。

ex02・ex03 は期待出力が規定されていないので、どちらでもよい。
本リポジトリの参考実装では、ログを出さない ex03 だけ案B（初期化リスト）にしてある。
どちらにせよ **「なぜ初期化リストの方が速いか」** は必ず言えるようにする。

> **初期化リスト vs 代入**:
> `: _value(o._value)` は**生成と同時に値を入れる**（初期化）。
> `{ _value = o._value; }` は**一度 0 で作ってから上書き**（代入）。
> `int` なら差は小さいが、`std::string` やクラス型メンバだと「デフォルト構築 + 代入」の 2 回動く。
> さらに **`const` メンバ・参照メンバは初期化リストでしか初期化できない**（ex03 の `Point` で効いてくる）。

#### D-04: `operator=` の中身

| 案 | 実装 | メリット | デメリット |
|----|------|---------|-----------|
| **A（ex00 推奨）** | `_value = rhs.getRawBits();` | subject の期待出力（`getRawBits` ログ）と一致 | 自クラスなのに関数経由という不自然さ |
| B | `_value = rhs._value;` | 素直。`private` は同じクラス間なら見える | ex00 の期待出力から `getRawBits` ログが消える |

**自己代入チェック** `if (this != &rhs)` は、`int` だけのこのクラスでは**不要**（`a = a` でも壊れない）。
ただし **書いておくのは良い習慣**で、defense で「なぜ要るのか」を聞かれたら
「メモリを解放してから自分をコピーする型では、これが無いと解放済み領域を読む」と答える。

```cpp
Fixed &Fixed::operator=(Fixed const &rhs) {
    std::cout << "Copy assignment operator called" << std::endl;
    if (this != &rhs)
        _value = rhs.getRawBits();
    return *this;          // ← 戻り値が Fixed& なのは a = b = c を可能にするため
}
```

> **なぜ `Fixed &` を返すのか**: 組込み型は `a = b = c;` と書ける。
> `b = c` の結果（`b` 自身）を `a =` に渡すため、**自分への参照**を返す。
> `void` を返すと `a = b = c` がコンパイルエラーになる。`Fixed`（値）を返すと無駄なコピーが 1 回増える。

### 4.5 公開契約（design-by-contract の適用）

| ID | 操作 | 事前条件 | 事後条件 | 不変条件 |
|----|------|---------|---------|---------|

## 5. ex01 — より有用な Fixed へ（変換と出力）

### 5.1 追加要件

| 追加 | シグネチャ |
|------|-----------|
| int コンストラクタ | `Fixed(int const value);` |
| float コンストラクタ | `Fixed(float const value);` |
| float 変換 | `float toFloat(void) const;` |
| int 変換 | `int toInt(void) const;` |
| 出力演算子 | `std::ostream &operator<<(std::ostream &os, Fixed const &f);`（**非メンバ**） |

許可: `roundf`（`<cmath>`）

### 5.2 変換の数学

```text
  int  → fixed :  raw = value * 256
  float→ fixed :  raw = roundf(value * 256)     ← 四捨五入が要る
  fixed→ float :  value = raw / 256.0f
  fixed→ int   :  value = raw / 256   または  raw >> 8
```

**検算**（subject の期待出力が、この式で本当に出るか確認する）:

| 入力 | raw | 戻した値 | `std::cout` の表示 |
|------|-----|---------|-------------------|
| `10`（int） | `10*256 = 2560` | `10.0` | `10` |
| `42.42f` | `roundf(10859.52) = 10860` | `10860/256 = 42.421875` | **`42.4219`** ✓ |
| `1234.4321f` | `roundf(1234.4321f * 256) = 316015` | `316015/256 = 1234.43359375` | **`1234.43`** ✓ |

`std::cout` は既定で**有効数字 6 桁**なので `42.421875` → `42.4219` になる。
**ここが一致する＝ `roundf` を使っている証拠**。`(int)(value * 256)`（切り捨て）だと
`42.42f` は raw `10859` → `42.417969` となり、期待出力と**ずれる**。

### 5.3 設計判断

#### D-05: int → fixed のスケーリング ★負数の罠

| 案 | 実装 | メリット | デメリット |
|----|------|---------|-----------|
| A | `_value = value << _fractionalBits;` | 固定小数点らしい。速い | **負の値の左シフトは C++98 で未定義動作**。`Fixed(-1)` が理論上壊れる |
| **B（推奨）** | `_value = value * (1 << _fractionalBits);` | 負数でも定義済み。最適化後のコードはシフトと同じ | 見た目が少し冗長 |
| C | `_value = value * 256;` | 一番読みやすい | 256 が `_fractionalBits` と**二重管理**になる（8 を変えたら壊れる） |

**推奨: 案B。** `(1 << _fractionalBits)` は**定数同士の正のシフト**なので安全で、
かつ「8」という知識の出どころが `_fractionalBits` 1 箇所に保たれる。

> **C++98 の規格**: 左シフト `E1 << E2` は、`E1` が符号付きで**負の値**のとき**未定義**。
> 右シフト `E1 >> E2` は、`E1` が負のとき**処理系定義**（実際の gcc/clang は算術シフト = 床関数）。
> 「実際は動く」と「規格上正しい」は別。defense で聞かれる可能性のある良問。

#### D-06: float → fixed の丸め

```cpp
_value = static_cast<int>(roundf(value * static_cast<float>(1 << _fractionalBits)));
```

| 注意点 | 内容 |
|--------|------|
| `roundf` の名前空間 | `<cmath>` を include しても、C++98 では `std::roundf` が**規定されていない**（C99 由来）。`std::` を付けずに `roundf(...)` と書くのが安全。`-Werror` 環境でのトラブルの定番 |
| `roundf` の丸め方 | **0 から遠い方へ四捨五入**（`roundf(-0.5f) == -1.0f`）。`floor(x+0.5)` とは負数で挙動が違う |
| キャスト | `roundf` は `float` を返すので `int` への明示キャストが要る。無いと `-Wconversion` 系で怒られることがある |

#### D-07: `toInt()` の丸め方向 ★ 自分で決めて文書化する

subject は正の値の例しか出さないので、**負数の仕様は自分で決める**（Skill 集が言う「人間が持つ判断」）。

| 案 | 実装 | `Fixed(-42.42f).toInt()` | 意味 | メリット | デメリット |
|----|------|------------------------|------|---------|-----------|
| **A（推奨）** | `return _value >> _fractionalBits;` | `-43` | **床関数**（常に小さい方へ） | 速い。全値域で一貫。実装が 1 行 | 規格上は処理系定義（実務上は全主要コンパイラで算術シフト） |
| B | `return _value / (1 << _fractionalBits);` | `-42` | **0 方向切り捨て**（`int` キャストと同じ） | `(int)float` と直感が一致。C++11 以降は規格で 0 方向に確定 | C++98 では負数の丸めは処理系定義。0 を境に刻みが不連続（-1..1 が全部 0 側に寄る） |
| C | `return static_cast<int>(roundf(toFloat()));` | `-42` | **四捨五入** | 「一番近い整数」で直感的 | `float` 経由で余計な誤差。`toFloat` の精度に依存 |

**推奨: 案A（床関数）**＋ **ヘッダのコメントに「負方向に丸める」と書く**。
理由: 分解能が一定という固定小数点の性質と、丸め方向も一定である方が整合する。
**案B を選んでもよい。重要なのは「決めて、書いて、テストがある」こと。**

#### D-08: `operator<<` をどこに置くか

| 案 | 形 | 可否 |
|----|---|------|
| メンバ関数 `Fixed::operator<<` | `f << std::cout` と書くことになる | **不可**（左辺が `ostream` でないと `std::cout << f` にならない） |
| **非メンバ関数 + public な `toFloat()`（推奨）** | `std::ostream &operator<<(std::ostream &, Fixed const &)` | **可**。`_value` に触らないので `friend` 不要 |
| 非メンバ + `friend` | 同上 | **禁止**（subject: `friend` は -42 点） |

```cpp
// Fixed.hpp（クラス定義の「外」に宣言）
std::ostream &operator<<(std::ostream &os, Fixed const &value);

// Fixed.cpp（定義はこちら。ヘッダに書くと 0 点）
```

| 設計上のポイント | 理由 |
|-----------------|------|
| 第 1 引数は `std::ostream &`（`const` 不可） | 出力はストリームの**状態を変える**から |
| 第 2 引数は `Fixed const &` | コピーを作らない（コンストラクタログが暴発しない）＋ `Fixed const c` も渡せる |
| 戻り値は `std::ostream &` | `std::cout << a << b << std::endl;` の連鎖のため |

#### D-09: 暗黙変換を許すか（`explicit` を付けるか）★ 理解の分かれ目

`Fixed(int const)` に `explicit` を**付けない**と、コンパイラは勝手に変換する。

```cpp
Fixed a;
a = 5;                      // OK: Fixed(5) が暗黙に作られて operator= に渡る
Fixed b = 42.42f;           // OK: Fixed(42.42f) の暗黙変換
void f(Fixed x);  f(3);     // OK: 暗黙変換
```

| 案 | メリット | デメリット |
|----|---------|-----------|
| **A: `explicit` なし（推奨）** | 組込み型らしく書ける。ex02 で `a * 2` のような式が自然に通る。subject の例も暗黙変換を前提にしている | 意図しない変換が静かに起きる |
| B: `explicit` を付ける | 事故防止。`Fixed(5)` と明示させる | **ex02 以降で `Fixed` と `int` の混在式が書けなくなる**。subject の意図に反する |

**推奨: 案A（付けない）。** ただし defense では
「`explicit` を付ければ暗黙変換を禁止できるが、数値型なので意図的に許している」と言えること。

> **⚠ 落とし穴**: `Fixed(int)` と `Fixed(float)` の**両方**があるとき、
> `Fixed x(5.05);` （`f` なしの `double` リテラル）は **`int` と `float` のどちらへの変換も同ランク → 曖昧でコンパイルエラー**。
> テストコードでは必ず `5.05f` と書くこと。これは実際によくハマる。

### 6.2 設計判断

#### D-10: 比較演算子をどう書くか

| 案 | 内容 | メリット | デメリット |
|----|------|---------|-----------|
| A | 6 個すべて `_value` 直接比較で独立に書く | 各行が最速・最短 | 6 箇所に同じ知識。`<` の意味を変えたら 6 箇所直す |
| **B（推奨）** | `<` と `==` を基本にし、残り 4 つをそこから導く | 比較の意味が**1 箇所**。矛盾（`a<b` かつ `a==b` 等）が原理的に起きない | 関数呼び出しが 1 段増える（インライン化されるので実質差なし） |

```cpp
bool Fixed::operator<(Fixed const &rhs) const  { return _value <  rhs._value; }
bool Fixed::operator==(Fixed const &rhs) const { return _value == rhs._value; }

bool Fixed::operator>(Fixed const &rhs) const  { return rhs < *this; }       // 引数を入れ替えるだけ
bool Fixed::operator<=(Fixed const &rhs) const { return !(rhs < *this); }
bool Fixed::operator>=(Fixed const &rhs) const { return !(*this < rhs); }
bool Fixed::operator!=(Fixed const &rhs) const { return !(*this == rhs); }
```

これは Skill 集の Hard Gate「**同じ目的と不変条件の責務を一箇所に集める**」の実例。
「6 個ベタ書きしないのは手抜き」ではなく、**意味の正本を 1 つにする**設計。

> **なぜ raw のまま比較してよいのか**: 両者ともスケールが同じ \(2^8\) なので、
> `a/256 < b/256` ⇔ `a < b`。**割り算が不要**。これが固定小数点の強み。

#### D-11: 算術演算子の実装方式 ★ 本モジュール最大の判断

| 案 | 実装 | 加減算の精度 | 乗除算の精度 | 値域 | 評価 |
|----|------|------------|------------|------|------|
| **A（推奨）** | **raw で整数演算**。`+`/`-` は raw の加減、`*`/`/` はスケール調整 | **厳密**（誤差ゼロ） | 丸め 1 回 | 中間オーバーフローに注意 | 固定小数点の**本質を学べる**。defense で強い |
| B | すべて `float` 経由：`Fixed(toFloat() OP rhs.toFloat())` | 大きな値で `float` の誤差が混入 | 丸め 2 回（float 演算 + 再量子化） | 中間があふれにくい | 5 分で書ける。**ただし「固定小数点を作った意味」が消える** |
| C | A + 中間を `double` に | 厳密 | 良好 | 広い | `double` 依存。組込み想定と矛盾 |

**推奨: 案A。** 理由は 3.3 の品質順位「数値的正しさ > 値域」。
そして何より、**加減算が誤差ゼロであることが固定小数点を使う最大の理由**だから、
そこを `float` 経由で潰す案B は問題設定と矛盾する（problem-framing の「目的に戻る」）。

```text
  加算:  raw_result = raw_a + raw_b                       （スケールはそのまま 2^8）
  減算:  raw_result = raw_a - raw_b

  乗算:  (a/256) * (b/256) = (a*b)/65536
         欲しいのは result/256 なので →  raw_result = (a*b) / 256
         ※ a*b は最大 62bit 必要 → 中間で long にする

  除算:  (a/256) / (b/256) = a/b
         欲しいのは result/256 なので →  raw_result = (a * 256) / b
         ※ 先に 256 倍してから割る。順序を逆にすると精度が壊滅する
```

**検算**: `Fixed(5.05f) * Fixed(2)`
raw は `1293` と `512` → `1293 * 512 / 256 = 2586` → `2586/256 = 10.1015625` → 表示 **`10.1016`** ✓（subject 一致）

#### D-12: 乗除算の中間型

| 案 | 型 | メリット | デメリット |
|----|---|---------|-----------|
| A | `int` のまま | 追加コードなし | `Fixed(1000) * Fixed(1000)` で**即オーバーフロー**（`256000 * 256000 = 6.5e10` > `2^31`） |
| **B（推奨）** | `long` にキャスト | 42 の環境（Linux / macOS の LP64）では 64bit。実用値域をほぼカバー | Windows (LLP64) では `long` が 32bit。**移植性の注釈が必要** |
| C | `long long` | 確実に 64bit | **C++98 に存在しない**。`-std=c++98 -pedantic` で警告 → `-Werror` で死ぬ |
| D | `double` 経由 | 桁が広い | 精度の議論が濁る |

**推奨: 案B（`long`）** ＋ ヘッダかコメントに「64bit 環境を前提」と一言。
「`long long` を使いたいが C++98 なので使えない」と言えることが、そのまま学習の証明になる。

```cpp
Fixed Fixed::operator*(Fixed const &rhs) const {
    long const product = static_cast<long>(_value) * static_cast<long>(rhs._value);
    // product を 2^8 で割って raw に戻す（負数の >> を避けるなら / を使う）
    ...
}
```

#### D-13: 計算結果の `Fixed` をどう作るか

`_value` に直接値を入れた `Fixed` が欲しいが、「raw から作るコンストラクタ」は subject にない。

| 案 | 実装 | メリット | デメリット |
|----|------|---------|-----------|
| **A（推奨）** | `Fixed result; result.setRawBits(x); return result;` | 追加メンバ不要。既存の public API だけで完結 | `Default constructor called` のログが演算のたびに出る（subject の ex02 例は「ログ省略」と明記しているので問題なし） |
| B | private コンストラクタ `Fixed(int raw, bool isRaw);` を足す | 1 行で書ける。意図が明確 | OCF 以外のコンストラクタが増え、`Fixed(5, true)` の意味を説明する手間 |
| C | `Fixed(toFloat() + rhs.toFloat())` で作る | 短い | D-11 案B と同じ欠点（精度が落ちる） |

**推奨: 案A**（追加概念ゼロが最優先。時間が無いときほど効く）。

#### D-14: インクリメント / デクリメント

```cpp
Fixed &operator++(void);        // 前置 ++a : 自分を変えて「自分への参照」を返す
Fixed  operator++(int);         // 後置 a++ : 変える前の「コピー」を返す
```

| 項目 | 説明 |
|------|------|
| `int` の引数 | **ダミー**。前置と後置を区別するための C++ の約束（値は使わない） |
| 前置の戻り値 | `Fixed &` — コピー不要で速い。`++(++a)` も書ける |
| 後置の戻り値 | `Fixed`（値）— 「**変更前の値**」を返す必要があるので、コピーが避けられない |
| 増減量 | raw を **1** だけ増減（= `0.00390625`）。subject の ε の定義そのもの |
| 実装の DRY | 後置は前置を使って書く: `Fixed tmp(*this); ++(*this); return tmp;` |

> **なぜ「前置の方が速い」と言われるか**: 後置は**コピーを 1 個作る**から。
> `int` なら誤差の範囲だが、重いクラスでは効く。C++ で `for (i = 0; i < n; ++i)` と
> 前置で書く習慣は、ここから来ている。ex02 はそれを実物で体験できる。
>
> **`-Wextra` の罠**: `Fixed operator++(int)` の仮引数に名前を付けると
> 「未使用引数」警告 → `-Werror` で失敗する。**名前を書かない**（`(int)` だけ）のが正解。

#### D-15: `min` / `max` が 4 つ必要な理由 ★

```cpp
static Fixed       &min(Fixed &a, Fixed &b);
static Fixed const &min(Fixed const &a, Fixed const &b);
static Fixed       &max(Fixed &a, Fixed &b);
static Fixed const &max(Fixed const &a, Fixed const &b);
```

subject の `main` にこれがある:

```cpp
Fixed a;                                  // 非 const
Fixed const b( Fixed(5.05f) * Fixed(2) ); // const
std::cout << Fixed::max( a, b ) << std::endl;
```

`b` は `const` なので **`max(Fixed&, Fixed&)` は呼べない**（const を外す変換は不可）。
`max(Fixed const&, Fixed const&)` だけが適合する → **const 版が無いとコンパイルエラー**。
逆に両方 `const` 版しか無いと、`max(a, b)` の結果に代入できない（`Fixed::max(x,y) = z;` のような用法）。

| 呼び出し | 選ばれる版 | 理由 |
|---------|-----------|------|
| `max(非const, 非const)` | 非 const 版 | より良い一致（`const` 追加は変換コスト扱い） |
| `max(非const, const)` | const 版 | 非 const 版は 2 番目の引数で不一致 |
| `max(const, const)` | const 版 | 唯一の候補 |

| 項目 | 説明 |
|------|------|
| `static` である理由 | `Fixed::max(a, b)` と**クラス名から**呼ぶ。特定のインスタンスに属さない操作だから |
| 参照を返す理由 | 「**どちらか**を返す」であってコピーを作らない。`min(a,b).setRawBits(0)` で元が変わる |
| `static` と `const` | `static` メンバ関数に末尾 `const` は**付けられない**（`this` が無いから）。付けるとコンパイルエラー |
| 同値のとき | `a == b` のときどちらを返すか。**決めて書く**（本設計: `a < b ? b : a` → **同値なら a を返す**） |

### 6.3 モデル欠落チェック

| 観点 | 内容 | 処遇 |
|------|------|------|
| 失敗: **0 除算** | `Fixed(1) / Fixed(0)` | raw 方式 → **整数の 0 除算 = クラッシュ（SIGFPE）**。subject が明示的に許容。float 方式なら `inf` → `int` キャストで未定義 |
| 失敗: 乗算オーバーフロー | 大きい値同士 | `long` 中間で緩和。それでも超えたら未定義（文書化して受け入れ） |
| 失敗: 加算オーバーフロー | `raw_a + raw_b` が `int` を超える | 未定義。subject 範囲外として N/A（**理由を言えること**） |
| 不変条件 | 全演算の結果もスケール \(2^8\) を保つ | `*` と `/` のスケール調整が唯一の要注意箇所 |
| 非可換性 | `a / b != b / a`、`a - b != b - a` | テストで確認（T02-12） |

## 7. ex03 — BSP（三角形の内外判定）

### 7.1 追加要件

| 提出 | `Makefile`, `main.cpp`, `Fixed.{h,hpp}`, `Fixed.cpp`, `Point.{h,hpp}`, `Point.cpp`, `bsp.cpp` |
|------|---|

| 関数 | `bool bsp(Point const a, Point const b, Point const c, Point const point);` |
| 戻り値 | 内側 → `true`。**頂点上・辺上は `false`** |

### 7.2 設計判断

#### D-16: `const` メンバと代入演算子の矛盾 ★ このモジュール最大の罠

subject は `Fixed const _x;` を要求する。しかし OCF は代入演算子を要求する。
**`const` メンバは一度初期化したら変更できない** → **代入演算子は仕事ができない。**

```cpp
Point &Point::operator=(Point const &rhs) {
    _x = rhs._x;    // ← コンパイルエラー。_x は const
}
```

| 案 | 実装 | メリット | デメリット | 判定 |
|----|------|---------|-----------|------|
| **A（推奨）** | 代入演算子は**宣言・定義するが、何もしない**（`(void)rhs; return *this;`） | subject の OCF 要求と `const` 要求を両立。コンパイルが通る。**意味的に正直**（不変オブジェクトだから代入できない） | 「代入したのに変わらない」という驚き → **コメントで明示**する義務がある | ◎ |
| B | `const_cast<Fixed&>(_x) = rhs._x;` | 「代入できる」ようになる | **`const` オブジェクトの書き換えは未定義動作**。defense で確実に突かれる | ✕ |
| C | `_x` を非 const にして `getX() const` だけ公開 | 代入が自然に書ける | **subject の明示要求（`Fixed const` 属性）に違反** | ✕ |
| D | 代入演算子を private 宣言のみ（定義しない） | 誤用をコンパイル時に禁止 | OCF の「4 つを実装する」要求から外れて見える | △ |

**推奨: 案A。** そしてヘッダにこう書く。

```cpp
// Point は不変（immutable）な値オブジェクト。
// _x / _y が const のため代入は値を変更できない。OCF 要求により定義のみ存在する。
Point &operator=(Point const &rhs);
```

> **⚠ 案A の代償（実測で確認済み）**: no-op の `operator=` を書くと、
> `std::vector<Point>` の `erase` / `insert` / `sort` が**コンパイルは通るのに結果だけ静かに壊れる**。
> `operator=` を書かなければコンパイルエラーで止まるので、**エラーを消したのではなく発見を先送りした**ことになる。
> だからヘッダのコメントは飾りではなく**必須**。詳細は `knowledge.md` の 4.8(1)。

> **なぜコピー「コンストラクタ」は書けるのか**: `const` メンバも**初期化はできる**（代入はできない）。
> 初期化リスト `: _x(other._x), _y(other._y)` なら合法。
> **初期化と代入は別物** という D-03 の話が、ここで効いてくる。

#### D-17: `Point` の追加メンバ（「その他有用なもの」）

| 必要なもの | 形 | 理由 |
|-----------|---|------|
| ゲッタ | `Fixed getX(void) const;` `Fixed getY(void) const;` | `bsp` が座標を読むため。`private` のままでは読めず、`friend` は禁止 |
| 戻り値の型 | 値返し `Fixed` か `Fixed const &` | 値返しで十分（`Fixed` は `int` 1 個）。`const &` ならコピーゼロだがログ差が出ない分どちらでも可 |

`bsp` は非メンバ関数なので、**public なゲッタが無いと書けない**。
これは「公開境界（interface-implementation-separation）」の実例:
`_x` が `Fixed` であることは公開するが、`Fixed` の内部が `int` であることは公開しない。

#### D-18: `bsp` のアルゴリズム ★

| 案 | 方法 | メリット | デメリット | 判定 |
|----|------|---------|-----------|------|
| **A（推奨）** | **外積の符号（same-side test）** | 割り算ゼロ、整数だけで完結 → **誤差ゼロ**。辺上判定（外積 = 0）が自然に出る | 外積の意味を理解する必要がある | ◎ |
| B | 重心座標（barycentric） | 「どのくらい内側か」も分かる | 割り算が入る → 丸め誤差。辺上の厳密判定が難しい | ○ |
| C | 面積の和が一致するか | 直感的 | **浮動小数点の等値比較**が必要 → 固定小数点の丸めで簡単に壊れる | △ |
| D | レイキャスティング | 任意多角形に使える | 三角形には過剰。辺上・頂点上の特殊処理が煩雑 | ✕ |

**推奨: 案A。**

**外積（cross product）とは**: 2D では 2 本のベクトルから 1 個のスカラーを作る。

```text
  cross(u, v) = u.x * v.y - u.y * v.x

  結果 > 0  →  v は u から見て「左（反時計回り）」
  結果 < 0  →  v は u から見て「右（時計回り）」
  結果 = 0  →  u と v は平行（= 同じ直線上）
```

三角形の内外判定は、**3 辺すべてに対して点が同じ側にあるか**を見る。

```text
       c
       /\            辺 a→b から見て p は左か右か
      /  \           辺 b→c から見て p は左か右か
     /  p \          辺 c→a から見て p は左か右か
    /______\
   a        b        3 つとも同じ符号  →  内側（true）
                     1 つでも 0        →  辺上 or 頂点上（false）
                     符号が混在        →  外側（false）
```

```text
  d1 = cross(b - a, p - a)
  d2 = cross(c - b, p - b)
  d3 = cross(a - c, p - c)

  if (d1 == 0 || d2 == 0 || d3 == 0)  return false;    // 辺上・頂点上・辺の延長線上
  return (d1 > 0 && d2 > 0 && d3 > 0) || (d1 < 0 && d2 < 0 && d3 < 0);
```

この式は **a, b, c の並び順（時計回り／反時計回り）に依存しない**のが利点。
また `a, b, c` が一直線（つぶれた三角形）なら 3 つとも 0 になり、自動的に `false`。

#### D-19: `bsp` の計算をどの型で行うか ★ 重要な洞察

| 案 | 計算型 | 誤差 | 判定 |
|----|-------|------|------|
| **A（推奨）** | `Fixed` の**差を取って `getRawBits()` で取り出し、`long` で掛ける** | **完全にゼロ** | ◎ |
| B | `Fixed` の演算子（`operator*`）で計算 | `*` が raw を 256 で割り直すため**下位ビットが落ちる** → 辺の近くで誤判定 | △ |
| C | `toFloat()` して `float` で計算 | `float` 誤差。`== 0` の判定が不安定 | ✕ |

**核心**: `bsp` が必要なのは**符号だけ**で、値の大きさは要らない。
だから**スケールを揃え直す必要がない**。raw のまま掛ければ結果のスケールは \(2^{16}\) になるが、
**符号は変わらない**ので判定には十分。→ **丸めが一度も起きない = 完全に厳密**。

```cpp
// bsp.cpp（ファイル内 static ヘルパ）
static long cross(Point const &o, Point const &p, Point const &q) {
    long const ax = (p.getX() - o.getX()).getRawBits();   // Fixed の減算は厳密
    long const ay = (p.getY() - o.getY()).getRawBits();
    long const bx = (q.getX() - o.getX()).getRawBits();
    long const by = (q.getY() - o.getY()).getRawBits();
    return ax * by - ay * bx;                              // long で掛ける（オーバーフロー回避）
}
```

> `getRawBits()` は public なので `friend` は不要。
> ヘルパを `static`（内部リンケージ）にすると `bsp.cpp` の外から見えず、公開面が汚れない。

#### D-20: `bsp` の引数が「値渡し」である意味

```cpp
bool bsp(Point const a, Point const b, Point const c, Point const point);
```

subject は `Point const &` ではなく **`Point const`（値渡し）** を指定している。

| 事実 | 意味 |
|------|------|
| 呼び出しごとに **4 回のコピーコンストラクタ**が走る | ログを出していれば目に見える |
| `const` メンバがあってもコピー構築は合法 | D-16 の「初期化と代入は別」の実証 |
| 参照渡しより遅い | が、subject の指定なので**変えない**。「参照の方が速いと分かっているが仕様に従った」と言えること |

| T03-19 | Point のコピー | `Point p(1,2); Point q(p);` | `q.getX() == 1` |
| T03-20 | Point の代入 ★ | `Point p(1,2), q(3,4); q = p;` | **コンパイルが通る**。値は変わらない。**その理由を説明できること**（D-16） |
| T03-21 | Point のデフォルト | `Point p;` | `(0, 0)` |
| T03-22 | const 正当性 | `Point const p(1,2); p.getX();` | 通る |
| T03-23 | 値渡しのコピー回数 | `bsp` を 1 回呼ぶ | `Copy constructor called` が **4 回**（D-20） |
| T03-24 | ビルド | `-Wall -Wextra -Werror -std=c++98` | 警告ゼロ |

## 9. このモジュールで学べること（総まとめ）

### 9.1 数値表現

| 学ぶこと | 中身 |
|---------|------|
| 固定小数点数の原理 | スケールを固定した整数表現。Q23.8 形式 |
| 分解能と値域の trade-off | 小数部ビットを増やす = 精度↑ 値域↓。8bit はその妥協点 |
| IEEE 754 の仕組み | 符号 1 / 指数 8 / 仮数 23 bit。**値が大きいほど刻みが粗くなる**理由 |
| `float` の危険 | `0.1f + 0.2f != 0.3f`、`==` 比較の危うさ、NaN / Inf / -0.0 |
| 丸めの種類 | 切り捨て（truncate）/ 床（floor）/ 四捨五入（round-half-away-from-zero = `roundf`）/ 偶数丸め |
| 量子化誤差 | 最大 ε/2 = 1/512。ε 未満の差は**存在しないのと同じ** |
| 固定小数点の使い所 | 組込み / DSP / ゲームの座標 / 金額計算（銀行は 10 進固定小数点） |

### 9.2 C++ のクラス設計

| 学ぶこと | 中身 |
|---------|------|
| OCF / Rule of Three | 4 つの特殊メンバ関数。**なぜ必要か**（シャローコピーと二重解放） |
| 暗黙生成 | 書かなければコンパイラが作る。作られるものと作られないものの境界 |
| 初期化 vs 代入 | 初期化リストの優先。`const` / 参照メンバは初期化リスト**専用** |
| 初期化順序 | メンバは**宣言順**に初期化される（初期化リストの順ではない）。`-Wextra` が警告する |
| オブジェクトの寿命 | スコープ、生成の逆順で破棄、**一時オブジェクトは完全式の終わりで破棄** |
| 値オブジェクト | 状態機械ではなく「値」を表す型の設計（不変 / 等値性 / コピー可能） |
| `static` メンバ変数 | クラスに 1 個。`sizeof` に含まれない。宣言と定義の分離 |
| `static` メンバ関数 | `this` が無い。`const` を付けられない。`Class::f()` で呼ぶ |
| アクセス指定子 | `private` は「クラス単位」（同じクラスの別インスタンスの private は見える） |
| `friend` を使わない設計 | public なアクセサ経由で非メンバ関数を書く技法 |

### 9.3 const correctness

| 学ぶこと | 中身 |
|---------|------|
| `const` メンバ関数 | オブジェクトを変えない約束。`const` オブジェクトから呼べるのはこれだけ |
| `const` 参照引数 | コピーを作らず、書き換えもしない。**引数の既定形** |
| `int const raw` | 値渡しの `const`。呼び出し側には影響しない（関数内で書き換えないという自分への宣言） |
| `const` オーバーロード | `min/max` の 4 つが示す、const 版・非 const 版の使い分け |
| 戻り値の `const` | `Fixed const &` を返す = 呼び出し側が結果を書き換えられない |
| `const_cast` の危険 | `const` オブジェクト本体の書き換えは未定義動作（D-16 案B） |

### 9.4 演算子オーバーロード（このモジュールの主題）

| 学ぶこと | 中身 |
|---------|------|
| アドホック多態性とは | **同じ記号 `+` が、型によって違う実装を選ぶ**こと。関数オーバーロードもこれ。（Module 04 の「サブタイプ多態性」＝仮想関数と対比） |
| メンバ vs 非メンバ | 左辺が自クラスならメンバで書ける。`std::cout << f` のように左辺が他人の型なら**非メンバ必須** |
| 戻り値型の設計 | `operator=` → `T&` / 比較 → `bool` / 算術 → `T`（値）/ 前置 `++` → `T&` / 後置 `++` → `T` |
| 前置と後置の区別 | ダミー `int` 引数という C++ の約束。性能差の理由 |
| `operator<<` の作法 | `ostream&` を受け取り `ostream&` を返す。`std::endl` を中で付けない |
| 演算子の意味を壊さない | `+` は可換に、`==` は反射的・対称的・推移的に。**直感に反する実装をしない** |
| 対称性の問題 | `fixed * 2` はメンバで書けるが `2 * fixed` は書けない（左辺が `int`）。非メンバにすれば両方通る、という設計上の知識 |
| オーバーロードできない演算子 | `::` `.` `.*` `?:` `sizeof` |
| 優先順位は変えられない | `a + b * c` の評価順は言語が決める |

### 9.5 型変換

| 学ぶこと | 中身 |
|---------|------|
| 変換コンストラクタ | 引数 1 個のコンストラクタは**暗黙の型変換器**になる |
| `explicit` | それを禁止するキーワード。付ける / 付けないの設計判断（D-09） |
| 暗黙変換の曖昧さ | `Fixed(int)` と `Fixed(float)` があるとき `Fixed(5.05)`（double）が**曖昧でエラー** |
| ユーザ定義変換は 1 段まで | `Fixed` → `int` → `char` のような連鎖は起きない |
| `static_cast` | C 形式キャスト `(int)x` より意図が明確で、検索できる |
| 整数昇格 | `char`/`short` は演算前に `int` へ。`int` 同士の演算結果は `int`（→ オーバーフロー） |

### 9.6 整数演算の罠（実務で一番効く知識）

| 学ぶこと | 中身 |
|---------|------|
| 左シフトの未定義動作 | 負の値の `<<` は C++98 で**未定義**（D-05） |
| 右シフトの処理系定義 | 負の値の `>>` は**処理系定義**（実際は算術シフト = floor） |
| 整数除算の丸め | **C++98 では負数の丸め方向は処理系定義**（C++11 で「0 方向切り捨て」に統一）。実際の全主要コンパイラは 0 方向 |
| 符号付きオーバーフロー | **未定義動作**。コンパイラは「起きない」前提で最適化する（だから危険） |
| 0 除算 | 整数では SIGFPE でクラッシュ。浮動小数点では `inf` |
| 型のサイズ | `int` = 32bit がほぼ全環境。`long` は LP64（Linux/macOS）で 64bit、LLP64（Windows）で 32bit |
| `long long` は C++11 | C++98 縛りでは使えない（D-12） |

### 9.7 設計スキル（mino skill suite 由来）

| 学ぶこと | 中身 |
|---------|------|
| 問題と手段を分ける | 「Fixed クラスを作る」は手段。問題は「一定分解能の数値型が無い」 |
| 契約で考える | 事前条件 / 事後条件 / 不変条件 / 失敗保証。テストは契約に紐づける |
| モデルの欠落監査 | 値制約・失敗・writer/reader を 1 つずつ見る。「表を埋めた」を完成としない |
| 公開境界の設計 | consumer が知るべき事と、隠すべき実装（`int` であること）を分ける |
| 品質の優先順位 | 全部を最大化しない。「値域は意図的に最適化しない」と**宣言**する |
| 未決は未決のまま残す | 丸め方向は人間が決める。AI や慣例に決めさせない |
| 証拠で判定する | 「コンパイルが通った」ではなく「負数・境界値のテストが通った」 |

### 9.8 幾何とアルゴリズム（ex03）

| 学ぶこと | 中身 |
|---------|------|
| 2D 外積 | `u.x*v.y - u.y*v.x`。符号 = 左右判定、絶対値 = 平行四辺形の面積 |
| same-side test | 3 辺すべてで同じ側 → 内側。順序非依存 |
| 重心座標 | 内分比による表現（案B）。補間で使う基礎 |
| 退化ケース | 面積 0 の三角形、同一点。**特別扱いせず自然に false になる式**を選ぶ価値 |
| 誤差に強い設計 | 「符号だけ要る」なら正規化しない。**割り算を避ける**のが幾何アルゴリズムの定石 |
| BSP（名前の由来） | Binary Space Partitioning。空間を平面/直線で再帰的に二分する技法（Doom のレンダリング等）。今回は「直線の片側判定」という**基礎部品**だけを実装している |

## 10. よくある失格・減点ポイント

| 重大度 | 内容 | 対策 |
|--------|------|------|
| **0 点** | ヘッダに関数の**実装**を書いた | `.hpp` は宣言のみ。`{ return _value; }` を書かない |
| **0 点** | インクルードガードが無い | `#ifndef FIXED_HPP` を全ヘッダに |
| **0 点** | ヘッダが単体で完結していない | `Fixed.hpp` に `#include <iostream>` を書く |
| **0 点** | `printf` / `malloc` / `free` を使った | 使わない |
| **-42 点** | `using namespace std;` を書いた | `std::` を毎回書く |
| **-42 点** | `friend` を使った | public アクセサ経由で書く（D-08 / D-17） |
| **-42 点** | STL コンテナ / `<algorithm>` を使った | `std::min` も禁止。自分で書く |
| 不合格 | C++11 の機能（`auto`, `nullptr`, `long long`, 範囲 for） | `-std=c++98` を付けてビルド確認 |
| 減点 | `-Werror` で落ちる（後置演算子の未使用引数など） | 仮引数に名前を付けない |
| 減点 | ex00 に ex02 の機能が入っている | ex ごとに subject 通りの範囲に |
| 減点 | 期待出力とメッセージの綴り・順序が違う | 全文 diff で確認 |
| 減点 | ex01 以降で `getRawBits` のログが出ている | 3.2 の表 |
| **defense 死** | 負数で壊れる（`toInt()`、乗算） | T01-10 / T02-09 / T02-11 |
| **defense 死** | 「なぜ 4 つの min/max が要るのか」に答えられない | D-15 |
| **defense 死** | 「なぜ OCF が要るのか」に「規則だから」と答える | 4.2 の二重解放の例で答える |

## 12. defense 想定問答

| 質問 | 答えの骨子 |
|------|-----------|
| 固定小数点とは？ | 整数を 256 倍した値として保持する。小数点の位置が固定なので刻み幅が常に一定 |
| なぜ 8 ビット？ | 分解能 1/256 と値域 ±838 万のバランス。subject 指定 |
| `float` と何が違う？ | `float` は値が大きいほど刻みが粗い。固定小数点は全域で一定。加減算が厳密 |
| OCF はなぜ必要？ | 暗黙生成はシャローコピー。ポインタを持つクラスで二重解放が起きる。ここで習慣づける |
| 初期化リストと代入の違いは？ | 初期化は生成と同時。代入はデフォルト構築後の上書き。`const`/参照メンバは初期化リスト専用 |
| `getRawBits` の `const` の意味は？ | オブジェクトを変更しない約束。`const Fixed` から呼ぶために必須 |
| `operator=` が参照を返す理由は？ | `a = b = c` の連鎖のため |
| 自己代入チェックは要る？ | このクラスでは不要（`int` だけ）。メモリを解放する型では必須 |
| なぜ `operator<<` は非メンバ？ | 左辺が `std::ostream` だから。メンバにすると `f << cout` になる |
| `friend` 無しでどう実装した？ | public な `toFloat()` 経由。内部表現を公開せずに済む |
| 後置 `++` の `int` は何？ | 前置と区別するためのダミー。値は使わない |
| 前置と後置どちらが速い？ | 前置。後置は変更前のコピーを 1 個作るため |
| min/max がなぜ 4 つ？ | 非 const 版と const 版の両方。`Fixed const b` を渡すと const 版しか適合しない |
| `static` メンバ関数に `const` を付けられる？ | 付けられない。`this` が無いため |
| 乗算はどう実装した？ | raw 同士を掛けて 256 で割る。中間で `long` にしてオーバーフローを避けた |
| `long long` を使わない理由は？ | C++98 に無い。`-std=c++98 -pedantic` で警告 |
| 0 除算は？ | 整数除算なので SIGFPE。subject がクラッシュを許容している |
| 負の値のシフトは？ | 左シフトは未定義、右シフトは処理系定義。だから `* (1 << n)` を使った |
| `toInt()` の負数の丸めは？ | 床関数（`-42.42` → `-43`）と決めて文書化した。0 方向切り捨てにする設計もある |
| `Point` の代入演算子は何をする？ | `const` メンバなので値を変えられない。OCF 要求により定義だけ存在する、意図的な no-op |
| `const` メンバなのにコピーコンストラクタは書ける？ | 初期化リストなら `const` メンバも初期化できる。初期化と代入は別 |
| `bsp` のアルゴリズムは？ | 3 辺の外積の符号。全部同符号なら内側、1 つでも 0 なら辺上で false |
| 辺上を false にする方法は？ | 外積が 0 = 直線上。その時点で false を返す |
| 誤差の影響は？ | 符号しか使わないので raw のまま `long` で掛けた。丸めが一度も起きず厳密 |
| 頂点の順序（時計/反時計）は？ | 結果に影響しない。「全部正 or 全部負」で判定しているため |
