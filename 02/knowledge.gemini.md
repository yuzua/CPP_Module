### [const メンバ変数とSTLコンテナ要件の衝突]
* **結論と実務の標準設計**: 
実務において、データクラスに `const` メンバ変数を持たせることは避けてください。不変性（Immutability）を担保したい場合は、「privateな非constメンバ変数」と「値を返す（またはconst参照を返す）publicなconstアクセサ（Getter）」の組み合わせによってカプセル化の枠組み内で保証するのが標準設計です。
* **原理・メカニズム**: 
C++における初期化と代入は全く異なる操作です。`const` メンバ変数はコンストラクタの初期化子リストでのみ値を設定でき、一度構築された後は一切の書き換えが言語仕様によって禁じられます。これにより、コンパイラはデフォルトの「コピー代入演算子（`operator=`）」を暗黙生成できなくなります。C++98のSTL標準コンテナ（`std::vector` など）は、要素型に対して `CopyConstructible`（コピー構築可能）かつ `Assignable`（代入可能）であることを強要します。`const` メンバがあるクラスは `Assignable` を満たさないため、根本的にコンテナとの相性が悪くなります。
* **具体的な罠・トレードオフ**: 
この制約を回避しようとして、OCFを満たすために「何も処理を行わない（no-opな）コピー代入演算子」を手書き実装すると、**コンパイルエラーが消え、代わりに致命的な実行時サイレントバグが発生**します。
具体的には、`std::vector<Point> points;` に対して `points.erase(points.begin());` を呼び出すと、内部では要素を前に詰めるためにコピー代入（`operator=`）が連続して呼ばれます。しかし、実装された代入演算子が空振りするため、要素は前方へ移動せず、単に末尾の要素の管理サイズが縮小されるだけになります。結果として `[1, 2, 3]` の先頭を消したはずが `[1, 2]` になる（2と3が残るべきなのに、代入処理が無視されて1と2が残存し、3が消滅する）という追跡困難なデータ破壊を引き起こします。

### [演算子オーバーロードの対称性と暗黙の型変換]
* **結論と実務の標準設計**: 
二項算術演算子（`+`, `-`, `*`, `/`）および比較演算子（`==`, `<` など）は、必ず「非メンバ関数」として実装してください。また、実装の正典として、まず複合代入演算子（`+=`, `*=` など）をクラスのメンバ関数として定義し、非メンバ関数である `operator+` の内部でその `+=` を呼び出して再利用（DRY原則）する設計をとります。
* **原理・メカニズム**: 
メンバ関数として `Fixed Fixed::operator+(Fixed const &rhs) const;` を定義した場合、左オペランドは呼び出し元のオブジェクト自身（`this`）に固定されます。C++のオーバーロード解決において、左オペランドが組み込み型（例: `int`）の場合、コンパイラはメンバ関数の検索を行いません。非メンバ関数 `Fixed operator+(Fixed const &lhs, Fixed const &rhs);` であれば、両辺の引数に対して平等に「暗黙の型変換（ユーザー定義の変換コンストラクタ `Fixed(int)` など）」が1段回まで適用されるため、完全な対称性が保証されます。
* **具体的な罠・トレードオフ**: 
二項演算子をメンバ関数にしてしまうと、`Fixed(3) + 2` は `Fixed(3).operator+(Fixed(2))` へと暗黙変換されてコンパイルが通るのに、`2 + Fixed(3)` はコンパイルエラーになるという歪なAPIが誕生します。
また、利便性を求めて変換演算子 `operator float() const;` を追加すると、今度は `Fixed(1) + Fixed(2)` という式を見たコンパイラが「Fixed同士の `operator+` を呼ぶべきか、両方をfloatに暗黙変換して組み込みのfloat加算を行うべきか」を判定できなくなり、致命的な「曖昧なオーバーロード解決（Ambiguous overload）」エラーでビルドが崩壊します。これを防ぐため、実務では `toFloat()` などの名前付き関数を用いて明示的な型変換を強制します。

### [一時オブジェクトの寿命とダングリング参照]
* **結論と実務の標準設計**: 
参照を返すAPI（特に `min` や `max` などのユーティリティ関数）を設計する際は、「戻り値の参照先オブジェクトの寿命が、引数として渡されたオブジェクトの寿命を決して超えない」という厳格な契約を認識し、ドキュメント化する必要があります。保証できない場合は値返し（Copy）を選択します。
* **原理・メカニズム**: 
C++において、式の中で生成された名前のない一時オブジェクト（例: `Fixed(1)`）の寿命は、その完全式（文の終わりの `;`）までです。通常、ローカルスコープで `const T &ref = 一時オブジェクト;` のように束縛すると、言語仕様の「寿命延長（Lifetime Extension）」が働き、参照のスコープを抜けるまで一時オブジェクトは生き延びます。しかし、**「関数をまたいで返された参照」に対してはこの寿命延長のルールは一切適用されません**。
* **具体的な罠・トレードオフ**: 
`Fixed const &r = Fixed::max(Fixed(1), Fixed(2));` と記述した瞬間、右辺の式が評価されて `min/max` の判定が行われた直後（セミコロンの位置）で `Fixed(1)` と `Fixed(2)` の一時オブジェクトのデストラクタが走り、メモリが破棄されます。結果として変数 `r` は破棄済みのメモリ領域を指すダングリング参照（Dangling Reference）となり、次の行で `std::cout << r;` と書いた時点で未定義動作（高確率でのガベージ値の出力やセグメンテーションフォルト）を引き起こします。これはC++標準ライブラリの `std::max` にも存在する悪名高い仕様の落とし穴です。

### [固定小数点数のスケーリングと未定義動作 (UB)]
* **結論と実務の標準設計**: 
整数値から固定小数点数（内部整数表現）へのスケーリング変換を行う際は、絶対に左シフト演算子（`<<`）を使用せず、乗算（例: `value * 256` や `value * (1 << 8)`）を使用してください。
* **原理・メカニズム**: 
C++（C++98〜C++11以降も同様）の規格において、「負の符号付き整数に対する左シフト（例: `-1 << 8`）」は明確な未定義動作（Undefined Behavior = UB）と定められています。右シフト（`>>`）を用いた負数の丸め方向も実装定義（Implementation-defined）です。コンパイラは最適化の過程で「プログラム内にUBは存在しない」という強烈な前提を置くため、UBを踏むとオーバーフローチェックのための `if` 文などがデッドコードと判定されて丸ごと削除されることがあります。
* **具体的な罠・トレードオフ**: 
「手元のgcc環境では `value << 8` でも負数が正しく算術シフトされたから大丈夫」と判断して実装すると、コンパイラのバージョンアップや `-O3` などの最適化フラグを付けた瞬間に挙動が壊れます。`-fsanitize=undefined`（UBSan）を付けて `Fixed(-1)` を実行すると `runtime error: left shift of negative value -1` が容赦なく検出されます。また、乗算によるオーバーフローを考慮せず、32bit整数同士を単純に掛け算して `(a * b) / 256` とすると、中間計算結果が32bitを超えた瞬間に符号付き整数オーバーフロー（これもUB）を起こし、符号が反転する壊滅的なバグを生みます。中間演算は必ず `long long`（LP64環境であれば `long`）にキャストしてから行う必要があります。

### [固定小数点数の代数法則の破綻（結合則）]
* **結論と実務の標準設計**: 
固定小数点数ライブラリを提供するアーキテクトは、その数値型が「乗算の結合則（Associativity）」および「分配則」を満たさないという代数的な限界を仕様書に明記しなければなりません。
* **原理・メカニズム**: 
固定小数点数の乗算は、内部整数同士を掛け合わせた後に、小数部のビット数分だけ右シフト（または除算）してスケールを戻す操作を伴います。この右シフトのたびに下位ビットの「切り捨て（または丸め）」が発生します。複数の乗算を連続して行う際、計算順序（カッコの位置）が変わると、どのタイミングでどの下位ビットが切り捨てられるかが変わるため、最終的な値が一致しなくなります。
* **具体的な罠・トレードオフ**: 
具体例として、`a = 2.0 (raw 512)`, `b = 0.00390625 (raw 1)`, `c = 0.5 (raw 128)` の計算を考えます。
左から計算する `(a * b) * c` の場合：
1. `a * b` = `(512 * 1) / 256` = `raw 2`
2. `raw 2 * c` = `(2 * 128) / 256` = `raw 1` (結果: 0.00390625)
右から計算する `a * (b * c)` の場合：
1. `b * c` = `(1 * 128) / 256` = `raw 0`（ここで下位ビットが切り捨てられ情報が完全消失する）
2. `a * raw 0` = `(512 * 0) / 256` = `raw 0` (結果: 0)
このように、浮動小数点数や数学的実数では同一になるはずの式が、固定小数点数では全く異なる結果を生みます。3Dグラフィックス等で変換行列を掛け合わせる順序を変えただけでオブジェクトが空間から消滅する原因となります。

### [幾何述語の頑健性と演算誤差の排除]
* **結論と実務の標準設計**: 
計算幾何学（BSPツリーの空間分割やポリゴンの表裏判定）において、アルゴリズム内に浮動小数点数の「割り算」や「三角関数（角度計算）」を決して持ち込んではいけません。判定は必ず「外積（Cross Product）」による面積の『符号』のみに依存した整数演算（厳密計算）で行います。
* **原理・メカニズム**: 
浮動小数点数（`float` / `double`）は2進数の有限小数であるため、0.1のような値は循環小数となり必ず丸め誤差を含みます。点Pが三角形ABCの内部にあるかどうかの判定は、重心座標系（Barycentric coordinates）のウェイト $\lambda_1, \lambda_2, \lambda_3$ がすべて $0 < \lambda < 1$ であるかで判定できます。この各 $\lambda$ は「部分三角形の面積 / 全体の面積」で求まりますが、面積は外積（ベクトルのクロス積）によって計算できます。ここでの核心は、内外判定に必要なのは「割合（厳密な実数値）」ではなく「面積の符号が3つとも一致しているか（すべて正か）」という位相情報だけである点です。したがって、全体面積で割る（正規化する）必要が数学的に存在しません。
* **具体的な罠・トレードオフ**: 
もし愚直に全体の面積で割り算を行って浮動小数点数で内外判定を実装してしまうと、点が三角形の辺の極めて近くにある場合や、三角形そのものが極端に細長い（退化三角形に近い）場合に、浮動小数点の丸め誤差（Machine Epsilon）によって本来負になるべき微小な外積値が正に反転し、「点が存在しないはずの空間に存在していると判定される」という致命的な幾何矛盾（Robustness Problem）を引き起こします。これが物理エンジンであれば、壁をすり抜けるバグ（トンネリング）に直結します。割り算を省き、固定小数点の内部表現（生ビットの整数値）だけで外積を計算すれば、桁あふれしない限り誤差は数学的にゼロになります。

### [コピー省略と出力ストリームの副作用]
* **結論と実務の標準設計**: 
`operator<<`（ストリーム挿入演算子）を実装する際は、受け取った `std::ostream` に対して `std::setprecision` や `std::fixed` などのマニピュレータを直接適用して放置してはいけません。必ず適用前のフォーマットフラグ（`ios_base::fmtflags`）を保存し、出力後に復元してください。また、コンパイラの最適化によるコンストラクタの呼び出し回数の変動を前提としたテストコードを書かないでください。
* **原理・メカニズム**: 
C++の入出力ストリーム（`std::cout` 等）は、内部にステートマシンを持っており、一度設定された精度や基数（16進数出力など）は、明示的にリセットされるまで後続のすべての出力に永続的な影響を与えます。
一方、オブジェクトの構築に関して、C++コンパイラには「コピー省略（Copy Elision：RVO/NRVO）」という強力な最適化が規格上許可されています。関数が一時オブジェクトを返す際、コンパイラは無駄なコピーコンストラクタの呼び出しを省き、受け取り側の変数のメモリアドレス上に直接オブジェクトを構築します。
* **具体的な罠・トレードオフ**: 
`operator<<` の中で見栄えを良くしようとして `os << std::setprecision(10) << value;` と実装すると、その関数を呼び出したユーザーの `std::cout` の状態が汚染されます。直後にユーザーが `std::cout << 3.14159f;` と出力した際、ユーザーの意図しない桁数で出力され、原因がどこにあるのか全く追えなくなります。
また、`Fixed const b(Fixed(5.05f) * Fixed(2));` というコードを実行した際、コンパイラのバージョンや最適化オプション（`-O0` vs `-O3`）によって一時オブジェクトのコピーが省略されるため、「Copy constructor called」というログの出力回数が変動します。この内部メカニズム（副作用の省略の合法性）を理解していないと、環境差分によるテスト落ちに対して無意味なデバッグ時間を費やすことになります。
