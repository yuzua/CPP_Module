### 1.2 訂正が必要な記述

#### 訂正 1 — Copy-and-Swap は「このモジュールでは使えない／使うべきでない」

> 元の記述: **Copy-and-Swap イディオム**: 例外安全性と自己代入への耐性を高めるコピー代入演算子の実装パターン。

イディオムの説明自体は正しい。しかし **Module 02 に適用しようとすると 3 つの壁**がある。

| 壁 | 内容 |
|----|------|
| ① **`std::swap` が使えない** | **C++98 では `std::swap` は `<algorithm>` に宣言されている**（C++11 で `<utility>` へ移動）。42 は Module 08 まで `<algorithm>` を禁止しているので、使うなら自前で `swap` を書く必要がある |
| ② **期待出力が壊れる** | 正準形は **引数を値で受ける**（`Fixed &operator=(Fixed rhs)`）。これによりコピーコンストラクタが 1 回余計に走り、subject の期待出力とログ数が合わなくなる |
| ③ **利点がゼロ** | Copy-and-Swap の価値は「**確保に失敗しても元の状態が壊れない**」こと。`Fixed` は `int` 1 個しか持たず例外を投げる操作が無いので、強い例外保証は最初から自明に成立している |

**正しい位置づけ**: 「知識として知っておく。ただし**資源を所有するクラス**（Module 03 以降の動的確保を持つクラス）で初めて意味を持つ」。

```cpp
// Copy-and-Swap の正準形（C++98、自前 swap 版）
class Buffer {
public:
    void swap(Buffer &other) {            // nothrow であることが前提
        char *tmp = this->_data;
        this->_data = other._data;
        other._data = tmp;
    }

    Buffer &operator=(Buffer rhs) {       // ← 値渡し。ここでコピーが作られる
        this->swap(rhs);                  // 中身を交換
        return *this;                     // rhs（＝古い自分）がここで破棄される
    }                                     // 自己代入チェックも不要になる
private:
    char *_data;
};
```

> **なぜ例外安全になるのか**: コピー（＝失敗しうる操作）を**関数に入る前**に済ませてしまう。
> 関数本体でやるのは `swap`（失敗しない）だけ。だから途中で例外が飛んでも `*this` は無傷。

#### 訂正 2 — 「ビットシフトによる変換」は負数で未定義動作になる

> 元の記述: `int`や`float`から固定小数点数へのビットシフトやスケーリング（×2^8など）を用いた変換ロジックを実装します。

| 方向 | よくある実装 | C++98 での扱い |
|------|-------------|---------------|
| `int` → fixed | `value << 8` | **`value` が負なら未定義動作（UB）** |
| `int` → fixed | `value * (1 << 8)` | ✅ 常に定義済み |
| fixed → `int` | `_value >> 8` | **`_value` が負なら処理系定義**（実際の gcc/clang は算術シフト＝床関数） |
| fixed → `int` | `_value / (1 << 8)` | C++98 では負数の丸め方向が処理系定義。C++11 で 0 方向に確定 |

規格の文言（C++11 [expr.shift]、C++98 も実質同じ解釈）:

> `E1 << E2` は、`E1` が符号付き型で**非負**かつ `E1 × 2^E2` が結果型で表現可能なら、その値。**それ以外は未定義**。

**「実際の gcc では動く」と「規格上正しい」は別物**。`-fsanitize=undefined` を付けると `Fixed(-1)` が
`shift exponent ... left shift of negative value` として実行時に検出される。

**正しい記述**: 「**左シフトではなく乗算でスケーリングする**。右シフトを使う場合は、負数の丸め方向が
処理系定義であることを理解したうえで仕様として明文化する」。

---

#### 訂正 3 — 「決定論的な演算精度」の根拠がずれている

> 元の記述: 浮動小数点数の処理が重い環境や決定論的な演算精度が求められる領域で使われる。

**IEEE 754 自体は完全に決定論的**である。同じ入力・同じ演算・同じ丸めモードなら、常に同じビット列が出る。
だから「float は非決定論的だから固定小数点を使う」という説明は**厳密には誤り**。

実務で非決定論に見える原因は、浮動小数点フォーマットではなく**その周辺**にある。

| 原因 | 内容 |
|------|------|
| **FMA 縮約** | `a*b + c` を 1 命令の融合積和にまとめると、中間丸めが 1 回減って**結果が変わる**。gcc の既定は `-ffp-contract=fast` |
| **x87 の余剰精度** | 32bit x86（SSE 無し）では中間計算が 80bit で行われ、レジスタに残るかメモリに書き出されるかで結果が変わる（`FLT_EVAL_METHOD`） |
| **`-ffast-math`** | 結合則の適用など、IEEE 754 が禁じている変形をコンパイラに許可する |
| **数学関数の実装差** | `sinf` などは規格が最終桁の正確性を保証していない。libc・OS・CPU で 1 ulp 違う |
| **自動ベクトル化** | 総和の加算順序が変わると結果が変わる（浮動小数点の加算は**結合則を満たさない**） |

固定小数点が決定論的なのは、**整数演算だけで閉じていて上記の要因が一切入らないから**。
だから対戦ゲームの lockstep 同期（全プレイヤーが同じ入力から同じ世界状態を再現する方式）や、
リプレイの再現性が要る領域で使われる。

**正しい記述**: 「浮動小数点の処理が重い／存在しない環境、および**プラットフォーム間でビット単位の
再現性**が要る領域で使われる。float が非決定論的なのではなく、float を扱うコンパイラ最適化と
ライブラリ実装に差があるため」。

### 1.3 表現を精密化したい記述

| # | 元の記述 | 精密化 |
|---|---------|--------|
| 1 | 「パフォーマンスと精度のバランスを取ります」 | 固定小数点が提供するのは**高い精度ではなく一定の分解能**。得るのは「値域全体で刻み幅が一定」「加減算が厳密」、失うのは「ダイナミックレンジ」。float は逆に、広い値域と引き換えに刻み幅が値の大きさに比例する |
| 2 | 「`explicit`: 意図しない暗黙の型変換を防ぐ設計」 | 概念は正しいが、**Module 02 では付けないのが subject の意図**。`a = 5;` や `Fixed(5.05f) * Fixed(2)` が暗黙変換に依存している。「付けられることを知ったうえで、数値型なので意図的に付けない」と説明できることがゴール。なお C++98 の `explicit` は**コンストラクタ専用**（変換演算子に付けられるのは C++11 から） |
| 3 | ex03「`const` メンバを初期化子リストで初期化する手法」 | 手法を学ぶだけでは半分。**核心はその代償**：`const` メンバがあると代入演算子が機能しなくなり、OCF の要求と衝突する。さらに C++98 の STL コンテナ要件（Assignable）も満たせなくなる |
| 4 | ex02「`min`/`max` のオーバーロード」 | `const` 対応に加えて、**参照を返すことの危険**（ダングリング参照）と、**同値のときどちらを返すかを決める必要がある**ことまでが到達点 |
| 5 | OCF「4 つを明示的に実装する設計ルール」 | 根拠は **Rule of Three**（デストラクタ / コピーコンストラクタ / コピー代入のどれか 1 つを書いたら 3 つ全部書け）。OCF はそれにデフォルトコンストラクタを足した 42 独自の呼称。C++11 以降は **Rule of Five**（+ ムーブ 2 つ）と **Rule of Zero**（何も書かないのが最善）へ発展している |

## 2. コア概念の精密版

### 2.1 Orthodox Canonical Form の本当の位置づけ

```text
  Rule of Zero（現代 C++ の第一選択）
    └ 資源を直接持たない。std::string / std::vector / スマートポインタに任せる
      → 特殊メンバ関数を 1 つも書かない。暗黙生成が常に正しい

  Rule of Three（C++98）
    └ デストラクタ・コピーコンストラクタ・コピー代入のどれか 1 つでも必要なら 3 つ全部必要
      理由: 1 つ必要ということは「浅いコピーでは壊れる資源」を持っている証拠

  Rule of Five（C++11）
    └ 上記 + ムーブコンストラクタ + ムーブ代入

  OCF（42 の呼称）
    └ Rule of Three + デフォルトコンストラクタ
```

**なぜ 42 は Rule of Zero ではなく OCF を強制するのか**: STL が使えないから。
Module 02〜07 では `std::vector` も `std::auto_ptr` も使えず、自分で `new`/`delete` を書く。
その世界では Rule of Three が必須になる。

**暗黙生成の規則（C++98）**

| 特殊メンバ | 暗黙生成される条件 | 生成される中身 |
|-----------|------------------|---------------|
| デフォルトコンストラクタ | **他のコンストラクタを 1 つも書いていない** とき | 各メンバをデフォルト構築（組込み型は**初期化されない**） |
| コピーコンストラクタ | 自分で書いていないとき | 各メンバをコピー構築（メンバ単位のコピー） |
| コピー代入 | 自分で書いていないとき | 各メンバをコピー代入 |
| デストラクタ | 自分で書いていないとき | 各メンバを破棄 |

> **罠**: `Fixed(int)` を 1 つ書いた瞬間、**デフォルトコンストラクタは暗黙生成されなくなる**。
> ex01 で `Fixed a;` が急にコンパイルエラーになるのはこれが原因（OCF を守っていれば起きない）。

**暗黙生成が「できない」ケース**（C++98 では宣言はされるが、使うと ill-formed）

- `const` メンバ／参照メンバがある → **コピー代入が作れない**（← `Point` がまさにこれ）
- コピー不可のメンバがある

### 2.2 多態性の 3 分類

Strachey / Cardelli の分類に基づく整理。**42 のモジュール構成そのもの**がこの分類に沿っている。

| 種類 | 別名 | 仕組み | 解決時期 | 42 での登場 |
|------|------|--------|---------|------------|
| **アドホック多態性** | オーバーロード | 同名の関数・演算子を型ごとに別実装 | **コンパイル時**（静的ディスパッチ） | **Module 02** |
| **サブタイプ多態性** | 包摂多態 / 継承 | 基底クラスのポインタ経由で派生の実装を呼ぶ | **実行時**（vtable 経由の動的ディスパッチ） | Module 03・04 |
| **パラメトリック多態性** | ジェネリクス | 型をパラメータ化し、1 つの実装を全型で共有 | コンパイル時（実体化） | Module 07（テンプレート） |

「アドホック（ad hoc = その場限りの）」という名前の由来は、**型ごとに実装をバラバラに用意するから**。
`int + int` と `Fixed + Fixed` に共通のコードは一切ない。
対してパラメトリック多態性は、1 つの `template <typename T> T add(T a, T b)` が全型を賄う。

**オーバーロード解決の優先順位**（`min`/`max` の話が腑に落ちる）

```text
  1. 完全一致（const の付加は「完全一致」の一種だが、より悪い一致とみなされる）
  2. 昇格（char → int, float → double）
  3. 標準変換（int → float, 派生 → 基底）
  4. ユーザー定義変換（Fixed(int) のような変換コンストラクタ）  ← 1 段まで
  5. 可変長引数
```

`Fixed::max(a, b)`（両方とも非 const）で非 const 版が選ばれるのは、`const` を足す方が
「悪い一致」だから。`Fixed::max(a, cb)` では非 const 版が候補から落ち、const 版だけが残る。

### 2.3 固定小数点数 — 何と引き換えに何を得るか

```text
    float (IEEE 754 単精度)                  Fixed (Q23.8)
  ┌─┬────────┬───────────────┐         ┌─┬──────────────────┬────────┐
  │S│ 指数 8 │   仮数 23     │         │S│   整数部 23      │小数部 8│
  └─┴────────┴───────────────┘         └─┴──────────────────┴────────┘
    小数点の位置が指数で動く                小数点の位置が固定

  値域  ±3.4e38                            ±8388608
  刻み  値に比例（相対誤差が一定）          常に 1/256（絶対誤差が一定）
  加算  丸めが入る                          整数加算そのもの（厳密）
  乗算  丸め 1 回                           スケール調整で丸め 1 回
```

| 観点 | float | Fixed |
|------|-------|-------|
| 誤差の性質 | **相対誤差**が一定（約 1.2e-7） | **絶対誤差**が一定（最大 1/512） |
| 1000000 付近の刻み | 約 0.0625 | 0.00390625（変わらない） |
| 0.000001 付近の刻み | 約 1e-13 | 0.00390625（**表せない**） |
| 加算の厳密性 | ✗ | ✅（桁あふれしない限り） |
| ハードウェア | FPU が要る | ALU だけで動く |

**使い分けの原則**: 「**値の大きさの幅が狭く、刻み幅の一定性が欲しい**」なら固定小数点。
「**桁が何十桁も動く**」なら浮動小数点。

**Q 記法（Qm.n）**: 整数部 m ビット、小数部 n ビット。本課題は 32bit 符号付きで n=8 なので
**Q23.8**（符号ビットを m に数えない TI 流）または **Q24.8**（符号を含める流儀）と書かれる。
**流儀が 2 つあるので、文書では必ず「符号ビットを含むか」を明示する**。

## 3. 各 Exercise の到達目標（追補版）

元のまとめの項目に、**抜けていた到達点**を太字で追加する。

### ex00

- コピーコンストラクタとコピー代入の呼び出しタイミングの違い
- `static const int` の意味と初期化方法
- 生ビット列の保持・取得・設定
- **「初期化」と「代入」は別の操作である**（コピーコンストラクタは初期化、`operator=` は代入）
- **`static const` のクラス内初期化と `.cpp` での定義の両方が要る理由**（ODR / odr-used）
- **`const` メンバ関数の意味**（`getRawBits` の末尾 `const`）
- **`operator=` が `Fixed &` を返す理由**（`a = b = c` の連鎖）
- **自己代入チェックが「今回は不要だが、資源を持つクラスでは必須」であること**
- **デストラクタの呼び出し順序が構築の逆順であること**

### ex01

- `int` / `float` からのスケーリング変換（**左シフトではなく乗算で**）
- `<<` を非メンバにする理由
- **`roundf` を使う理由**（切り捨てでは subject の `42.4219` にならない）
- **`roundf` は `std::` に入らない場合があるため無修飾で呼ぶ**（C99 由来の関数）
- **変換コンストラクタが暗黙の型変換器になること**と `explicit` の選択
- **`Fixed(int)` と `Fixed(float)` が両方あると `Fixed(5.05)`（double リテラル）が曖昧になる**
- **`operator<<` はストリームの書式状態を壊してはいけない**（`setprecision` を勝手に固定しない、`std::endl` を付けない）
- **`toInt()` の負数の丸め方向は自分で決めて文書化する**（subject は正の例しか示さない）

### ex02

- 算術・比較・増減演算子で「組込み型と同等の使い勝手」を実現
- 前置／後置のシグネチャと戻り値型の違い
- `const` / 非 `const` 両対応の `static min`/`max`
- **正典は `+=` を先に実装し、`+` をそれで書くこと**（→ 4.2）
- **メンバ演算子では `2 + fixed` が書けない**（対称性の問題）
- **比較 6 種は `<` と `==` から導ける**（意味の正本を 1 つにする）
- **乗除算の中間型とオーバーフロー**（C++98 に `long long` は無い）
- **除算のスケール調整順序**（先に 2^8 倍してから割る）
- **0 除算・桁あふれという「失敗契約」を明文化する**
- **`min`/`max` が参照を返すことによるダングリング参照の危険**
- **`min`/`max` が同値のときどちらを返すかを決める**
- **固定小数点の乗算は結合則を満たさない**

### ex03

- `const` メンバの初期化子リスト初期化
- 外積・重心座標による内外判定
- **`const` メンバは代入演算子を機能不全にする**（OCF 要求との衝突をどう解決するか）
- **「初期化はできるが代入はできない」という C++ の根本規則**
- **辺上・頂点上は `false` という契約を、外積 = 0 で自然に満たす**
- **退化三角形（面積 0）が特別扱いなしで `false` になること**
- **符号だけ必要なので正規化（割り算）が不要 → 丸め誤差ゼロ**
- **`Point const a` という値渡し引数の意味**（トップレベル `const` は関数の型に影響しない）
- **BSP という名前の実体**（今回作るのは BSP の中核プリミティブである「直線の片側判定」だけ）

## 4. さらに一歩踏み込む — シニアエンジニア視点

### 4.1 特殊メンバ関数の深掘り

#### (1) メンバの初期化順序は「宣言順」であって「初期化子リストの順」ではない

```cpp
class Bad {
    int _b;
    int _a;
public:
    Bad(int x) : _a(x), _b(_a * 2) {}   // ← _b が先に初期化される。_a はまだ未初期化
};
```

`-Wall` に含まれる `-Wreorder` が警告する。**初期化子リストの順序は宣言順に揃える**のが鉄則。

#### (2) コピー省略（copy elision）— 出力が処理系で変わる

C++98 は「コピーコンストラクタに副作用があっても、コンパイラはコピーを省略してよい」と
**明示的に許可**している（C++17 では prvalue について**義務化**）。

```cpp
Fixed const b(Fixed(5.05f) * Fixed(2));
```

`operator*` が返した一時オブジェクトから `b` を構築するが、**コンパイラは一時を直接 `b` の場所に作る**
ことができる（RVO）。結果として `Copy constructor called` が出たり出なかったりする。

| 用語 | 意味 |
|------|------|
| **RVO** | `return Fixed(...)` のように**名前のない**一時を返すときの省略 |
| **NRVO** | `Fixed result; ...; return result;` のように**名前付き**ローカルを返すときの省略（任意） |
| **C++17 の保証されたコピー省略** | prvalue からの初期化はそもそもコピーが「存在しない」ことになった |

**評価での使いどころ**: 「出力のコンストラクタ呼び出し回数が違う」と指摘されたら、
最適化レベルとコピー省略の話を出せる。`-fno-elide-constructors` を付けると省略を止められる。

#### (3) Most Vexing Parse

```cpp
Fixed a();     // ← 変数ではなく「Fixed を返す引数なしの関数 a」の宣言
Fixed a;       // ← 正しい
```

「関数宣言に解釈できるものは関数宣言と解釈する」という規則。`a.getRawBits()` で
「`a` はクラス型ではない」という謎のエラーが出たらこれ。

#### (4) コピー禁止クラスの作り方（C++98 と C++11）

```cpp
// C++98: private に宣言だけして定義しない（使うとリンクエラー）
class NonCopyable {
private:
    NonCopyable(NonCopyable const &);
    NonCopyable &operator=(NonCopyable const &);
};

// C++11: = delete（コンパイルエラーになるので診断が明快）
class NonCopyable {
    NonCopyable(NonCopyable const &) = delete;
    NonCopyable &operator=(NonCopyable const &) = delete;
};
```

#### (5) 一時オブジェクトの寿命

| 状況 | 寿命 |
|------|------|
| 式の中の一時 | **完全式の終わり**（`;` の位置）で破棄 |
| `const T &` に束縛した一時 | **参照の寿命まで延長される** |
| **関数が返した参照が指す一時** | **延長されない**（→ ダングリング。4.2(5) 参照） |

```cpp
Fixed const &r = Fixed(42);      // OK: r の寿命まで一時が生き延びる
```

### 4.2 演算子オーバーロードの正典

#### (1) `+=` を先に作り、`+` をそれで書く

これが C++ の標準的な設計順序。**加算の意味が 1 箇所にしか存在しなくなる**。

```cpp
Fixed &Fixed::operator+=(Fixed const &rhs) {
    this->_value += rhs._value;
    return *this;
}

Fixed Fixed::operator+(Fixed const &rhs) const {
    Fixed result(*this);
    result += rhs;
    return result;
}
```

Module 02 の subject は `+=` を要求していないので**今回は必須ではない**。
しかし「なぜ実務では `+=` が先なのか」を答えられると一段上に見える。

#### (2) メンバ演算子は対称性を壊す ★重要

```cpp
Fixed a(3);
a * 2;      // OK: Fixed::operator*(Fixed const&) + 2 の暗黙変換
2 * a;      // ✗ コンパイルエラー: int に Fixed を取る operator* は無い
```

**左オペランドの型がクラスでないと、メンバ演算子は候補にすらならない。**
`std::cout << f` を非メンバにした理由とまったく同じ問題が、算術演算子にも起きている。

```cpp
// 非メンバにすると両辺が対称になる
Fixed operator*(Fixed const &lhs, Fixed const &rhs);
// 2 * a  → Fixed(2) * a  （左辺も暗黙変換の対象になる）
```

| 演算子 | 推奨 | 理由 |
|--------|------|------|
| `=` `[]` `()` `->` | **メンバ必須**（言語規則） | — |
| `+= -= *= /=` | メンバ | 左辺を変更するので対称性が不要 |
| `+ - * /` `== != < > <= >=` | **非メンバ推奨** | 両辺に暗黙変換を効かせたいため |
| `<<` `>>`（ストリーム） | **非メンバ必須** | 左辺が `std::ostream` |
| `++ --` | メンバ | 左辺を変更する |

**ただし Module 02 の subject は「クラスに public メンバ関数を追加せよ」と明示している**ので、
今回はメンバで実装するのが正解。「非メンバの方が対称だと知ったうえで指示に従った」と言えること。

#### (3) 戻り値の型 — `const T` を返すべきか

```cpp
Fixed       operator+(Fixed const &rhs) const;   // 現代の推奨
Fixed const operator+(Fixed const &rhs) const;   // C++98 時代の推奨
```

| | `const` を付けると | 付けないと |
|---|---|---|
| 利点 | `(a + b) = c;` や `(a + b)++;` という無意味な式を**コンパイル時に禁止**できる | — |
| 欠点 | — | 上記が書けてしまう（ただし害は小さい） |
| **C++11 以降** | **ムーブが効かなくなる**（`const` からはムーブできない）→ **有害** | 推奨 |

Scott Meyers が *More Effective C++* Item 6 で後置インクリメントについて `const T` 返しを
推奨していたのは C++98 の文脈。**現代では付けない**のが標準。

#### (4) `operator<<` はストリームの状態を尊重する

```cpp
// 悪い例: 呼び出し側の書式設定を無視して固定してしまう
std::ostream &operator<<(std::ostream &os, Fixed const &v) {
    os << std::setprecision(10) << std::fixed << v.toFloat();   // ✗
    return os;
}
```

`std::cout << std::setprecision(2) << myFixed;` と書いたユーザーの意図を壊す。
さらに `setprecision` は**ストリームに永続的に残る**ので、後続の出力まで変わってしまう。

**原則**: `operator<<` は値を 1 つ流すだけ。`std::endl` も付けない。改行も書式も呼び出し側の自由。

書式を一時的に変えたい場合は、フラグを保存して復元する。

```cpp
std::ios_base::fmtflags const saved = os.flags();
std::streamsize const savedPrecision = os.precision();
// ... 変更して出力 ...
os.flags(saved);
os.precision(savedPrecision);
```

#### (5) 参照を返す `min` / `max` のダングリング参照 ★実務で刺さる

```cpp
Fixed const &r = Fixed::max(Fixed(1), Fixed(2));
std::cout << r << std::endl;   // ✗ 未定義動作: 一時はこの行の前に破棄済み
```

**関数が返した参照には寿命延長が働かない。** `Fixed::max` は引数への参照をそのまま返すので、
引数が一時オブジェクトだと、式が終わった瞬間に参照先が消える。

これは `std::max` にも存在する**既知の落とし穴**で、C++ 標準化委員会でも議論されてきた。

| 安全な使い方 | 危険な使い方 |
|-------------|-------------|
| `Fixed x(1), y(2); Fixed &r = Fixed::max(x, y);` | `Fixed const &r = Fixed::max(Fixed(1), Fixed(2));` |
| `std::cout << Fixed::max(a, b) << std::endl;`（その場で使い切る） | 参照を変数に保存して後で使う |

**設計の教訓**: 参照を返す API は「**引数より長生きしない**」という契約を持つ。
その契約を文書化できないなら値返しにする。

#### (6) 比較演算子の数学的な性質

`operator==` は **同値関係** を満たすべき。

| 性質 | 意味 |
|------|------|
| 反射律 | `a == a` は常に true |
| 対称律 | `a == b` なら `b == a` |
| 推移律 | `a == b` かつ `b == c` なら `a == c` |

`operator<` は **狭義弱順序（strict weak ordering）** を満たすべき。
これは `std::sort` や `std::map` が要求する条件で、**Module 08/09 で必須**になる。

| 条件 | 意味 |
|------|------|
| 非反射性 | `a < a` は false |
| 非対称性 | `a < b` なら `!(b < a)` |
| 推移性 | `a < b` かつ `b < c` なら `a < c` |
| 同値の推移性 | `!(a<b) && !(b<a)` を「同値」とすると、それも推移的 |

`Fixed` は `int` の比較に帰着するので全部満たす。**満たさない例**は「NaN を含む float」
（`NaN < x` も `x < NaN` も `NaN == NaN` も全部 false）。これが `std::sort` を壊す典型例。

#### (7) C++20 の三方比較演算子

```cpp
// C++20 なら 6 個が 1 行になる
auto operator<=>(Fixed const &rhs) const = default;
```

`<=>`（spaceship operator）は `std::strong_ordering` / `weak_ordering` / `partial_ordering` を返し、
コンパイラが `< > <= >=` を自動生成する。`==` だけは別途 `operator==` が必要。
**Module 02 で 6 個手書きする苦労が、言語機能として解決された**という歴史を知っておくとよい。

#### (8) `std::rel_ops`（C++98 の部分的解決）

`<utility>` の `std::rel_ops` 名前空間には、`==` と `<` から残り 4 つを導くテンプレートがある。
ただし名前空間全体を取り込むため衝突しやすく、**C++20 で非推奨**になった。
「自分で `<` と `==` から導く」という本課題の設計は、この考え方の手書き版。

### 4.3 型変換の設計

#### (1) `explicit` の判断基準

| 単一引数コンストラクタの性質 | 推奨 |
|---------------------------|------|
| **同じものの別表現**（`Fixed(int)`、`std::string(char const*)`） | 暗黙変換を許す（`explicit` なし） |
| **入力から別の概念を構築**（`std::vector(size_t n)`） | **`explicit` を付ける** |

`std::vector<int> v = 10;`（要素 10 個の vector）が書けてしまったら事故なので、
`std::vector` の `size_t` コンストラクタは `explicit` になっている。
一方 `std::string s = "hello";` は自然なので暗黙変換が許されている。

`Fixed(int)` は「同じ数値の別表現」なので**暗黙変換を許す側**。これが subject の設計。

#### (2) 変換演算子 `operator float()` の罠 ★入れてはいけない理由

「`toFloat()` より `operator float()` の方がスマートでは？」と考えるのは自然だが、**破綻する**。

```cpp
class Fixed {
public:
    Fixed(float const value);      // float → Fixed
    operator float() const;        // Fixed → float
};

Fixed a(1), b(2);
a + b;   // ✗ 曖昧: Fixed::operator+(Fixed) か、両辺を float にして float 同士の + か
```

**双方向の暗黙変換を用意すると、オーバーロード解決が曖昧になる。**
さらに `if (myFixed)` のような無意味な式まで通るようになる。

| 設計 | 評価 |
|------|------|
| 名前付き関数 `toFloat()` / `toInt()` | ✅ 意図が明示的。曖昧さが起きない |
| `operator float()` | ✗ 双方向変換で曖昧になる。暗黙に呼ばれる場所が読めない |
| C++11 `explicit operator bool()` | ✅ 例外的に有用（`if (ptr)` の実現に使われる安全な形） |

**`toFloat()` という名前付き関数は、スマートさを捨てて明示性を取った正しい設計**。

#### (3) ユーザー定義変換は 1 段まで

```cpp
class A { public: A(int); };
void f(A);
f(3);      // OK: int → A の 1 段
f('c');    // OK: char → int（標準変換）→ A（ユーザー定義変換）は合法
           //     標準変換 + ユーザー定義変換 1 回までは許される
```

ユーザー定義変換が **2 回連続**することはない。これを知らないと
「なぜこの変換が通らないのか」でハマる。

### 4.4 整数演算の正しさと未定義動作

#### (1) このモジュールに関係する UB / 処理系定義の一覧

| 操作 | C++98 での扱い | 検出方法 |
|------|--------------|---------|
| 負の値の左シフト `-1 << 8` | **未定義** | `-fsanitize=undefined` |
| シフト量が型幅以上 `x << 32` | **未定義** | 同上 |
| 負の値の右シフト `-1 >> 8` | **処理系定義**（実際は算術シフト） | — |
| 符号付き整数のオーバーフロー | **未定義** | `-fsanitize=signed-integer-overflow` |
| 整数の 0 除算 | **未定義**（実際は SIGFPE） | 実行時クラッシュ |
| `INT_MIN / -1` | **未定義**（オーバーフローするため） | `-fsanitize=undefined` |
| 範囲外の `float` → `int` 変換 | **未定義** | `-fsanitize=float-cast-overflow` |
| `NaN` / `inf` → `int` 変換 | **未定義** | 同上 |
| 符号なし整数のオーバーフロー | **定義済み**（2^n で折り返す） | — |

> **「UB は単にラップするだけ」ではない**。コンパイラは「UB は起きない」と仮定して最適化するので、
> `if (x + 1 < x)` のようなオーバーフロー検査が**丸ごと削除される**ことがある。

#### (2) 型サイズの移植性

| 型 | LP64（Linux / macOS） | LLP64（Windows） | ILP32（32bit） |
|----|---------------------|-----------------|---------------|
| `int` | 32 | 32 | 32 |
| `long` | **64** | **32** | 32 |
| `long long` | 64（C++11） | 64（C++11） | 64 |
| `void *` | 64 | 64 | 32 |

C++98 に `<cstdint>`（`int64_t` など）は無い。移植性が要るなら自前 typedef を書く。

```cpp
// C++98 で 64bit 整数が要るときの現実解
#if defined(_WIN32)
typedef __int64 Int64;
#else
typedef long long Int64;      // 厳密には C++98 外（gcc/clang の拡張）
#endif
```

**42 の環境は LP64 なので `long` で 64bit**。ただし「Windows では 32bit になる」ことを
コメントに残しておくのがプロの仕事。

#### (3) 整数昇格と通常の算術変換

```cpp
char a = 100, b = 100;
char c = a + b;          // a, b は int に昇格 → 200 → char に戻すとき処理系定義
```

`short` / `char` は演算前に `int` へ昇格する。`Fixed` の `_value` は `int` なので
この問題は起きないが、「なぜ `int` にしたのか」を聞かれたときの答えになる。

### 4.5 IEEE 754 の実像

#### (1) 単精度 float のビット構成

```text
  31 30      23 22                    0
  ┌─┬──────────┬───────────────────────┐
  │S│ 指数 8bit │      仮数 23bit        │
  └─┴──────────┴───────────────────────┘

  値 = (-1)^S × 1.仮数 × 2^(指数 - 127)      ← 正規化数
  仮数の先頭の「1.」は保存されない（ケチ表現）→ 実効 24bit
```

| 項目 | 値 |
|------|-----|
| 有効桁 | 24 bit ≈ 10 進 7.2 桁 |
| machine epsilon | 2^-23 ≈ 1.19e-7 |
| **整数を厳密に表せる上限** | **2^24 = 16777216**（16777217 は表せず 16777216 になる） |
| 正規化数の最小 | 約 1.18e-38 |
| 非正規化数（denormal） | それ以下。精度が落ちる。CPU によっては**極端に遅い** |

#### (2) 特殊値

| ビットパターン | 意味 | 性質 |
|--------------|------|------|
| 指数全 1・仮数 0 | ±∞ | `1.0f/0.0f` で生成。`int` への変換は UB |
| 指数全 1・仮数 ≠ 0 | NaN | **`NaN == NaN` は false**。比較がすべて false になる |
| 指数全 0・仮数 0 | ±0.0 | `-0.0 == +0.0` は **true** だがビット列は違う |
| 指数全 0・仮数 ≠ 0 | 非正規化数 | 0 の近傍を埋める |

```cpp
float nan = 0.0f / 0.0f;
nan == nan;    // false  ← これが std::sort を壊す
nan != nan;    // true   ← NaN 判定の古典的イディオム
```

#### (3) 厳密に表せる数 / 表せない数

`float` が厳密に表せるのは **2 進の有限小数（dyadic rational）** だけ。

| 値 | 厳密か |
|----|--------|
| `0.5`, `0.25`, `0.125`, `2.5` | ✅（分母が 2 の冪） |
| `0.1`, `0.2`, `0.3` | ✗（10 進の 1/3 と同じで、2 進では循環する） |
| `42.42` | ✗ |

**固定小数点も同じ制約を持つ**（分母が 256 の分数しか表せない）ので、
`Fixed(0.1f)` は `0.1015625` になる。この 2 段階の丸め（10 進 → float → fixed）を
説明できることが ex01 の到達点。

#### (4) 丸めモードの分類

| モード | 例: 2.5 → | 例: -2.5 → | 使われる場所 |
|--------|----------|-----------|-------------|
| 0 方向切り捨て（truncate） | 2 | -2 | C/C++ の `(int)` キャスト、整数除算 |
| 床（floor） | 2 | -3 | 算術右シフト、`std::floor` |
| 天井（ceil） | 3 | -2 | `std::ceil` |
| **0 から遠い方へ四捨五入** | **3** | **-3** | **`roundf` / `round`** |
| **最近接偶数（banker's rounding）** | **2** | **-2** | **IEEE 754 の既定丸め**、`rint` / `nearbyint` |

**なぜ IEEE 754 の既定が偶数丸めなのか**: 単純な四捨五入は「0.5 を常に切り上げる」ため、
**大量に足し合わせると誤差が一方向に偏る**（統計的バイアス）。偶数丸めは偏りを打ち消す。

会計システムが「銀行家の丸め」を使うのも同じ理由。

### 4.6 固定小数点の実務知識

#### (1) 乗算の丸め — 切り捨てではなく最近接に

本課題の実装は `(a*b) / 256` で**0 方向切り捨て**になっている。実務のライブラリは
**半分を足してからシフト**して最近接丸めにする。

```cpp
// 切り捨て（本課題の実装）
raw = (a * b) / 256;

// 最近接丸め（実務向け）
raw = (a * b + 128) >> 8;        // 128 = 2^(8-1) = 半分
```

| | 切り捨て | 最近接丸め |
|---|---|---|
| 誤差の範囲 | -1 〜 0 LSB | -0.5 〜 +0.5 LSB |
| 誤差の偏り | **常に 0 方向へ偏る**（累積すると効く） | 偏りが小さい |
| コスト | 同等 | 加算 1 回 |

**累積演算（フィルタ、行列積、積分）では切り捨ての偏りが致命的**になる。
DSP のライブラリが必ず丸め付きなのはこのため。

#### (2) 飽和演算（saturating arithmetic）

桁あふれ時に「折り返す」のではなく「上限／下限で止める」。

```text
  ラップアラウンド:  127 + 1  →  -128     （音声なら「バリッ」というノイズ）
  飽和:             127 + 1  →  127       （音声なら「歪み」で済む）
```

音声・画像処理では**飽和が標準**。x86 の SSE には飽和加算命令（`paddsw` 等）がある。
本課題は subject が許容しているので未定義のままでよいが、
「実務なら飽和させる」と言えると設計力が伝わる。

```cpp
// 飽和加算の考え方（C++98、<limits> 使用）
long const sum = static_cast<long>(a) + static_cast<long>(b);
if (sum > std::numeric_limits<int>::max())  return std::numeric_limits<int>::max();
if (sum < std::numeric_limits<int>::min())  return std::numeric_limits<int>::min();
return static_cast<int>(sum);
```

#### (3) 代数法則がどこまで成り立つか ★

| 法則 | 整数 | float | **Fixed** |
|------|------|-------|-----------|
| 加算の交換則 `a+b = b+a` | ✅ | ✅ | ✅ |
| 加算の結合則 `(a+b)+c = a+(b+c)` | ✅（桁あふれなし） | **✗** | ✅（桁あふれなし） |
| 乗算の交換則 `a*b = b*a` | ✅ | ✅ | ✅ |
| **乗算の結合則 `(a*b)*c = a*(b*c)`** | ✅ | **✗** | **✗** |
| 分配則 `a*(b+c) = a*b + a*c` | ✅ | ✗ | ✗ |
| `(a+b)-b = a` | ✅ | ✗ | ✅ |

**固定小数点の乗算が結合則を満たさない具体例**（本実装で確認済み）:

```text
  a = 2.0        (raw 512)
  b = 0.00390625 (raw 1)
  c = 0.5        (raw 128)

  (a*b)*c : a*b = 512*1/256   = raw 2   (0.0078125)
            2*128/256         = raw 1   → 0.00390625

  a*(b*c) : b*c = 1*128/256   = raw 0   (0 に丸められて消える)
            512*0/256         = raw 0   → 0
```

**中間で情報が失われるから**。数値型を設計する側は、この性質を仕様として明記する義務がある。
逆に **加算の結合則は成り立つ**のが固定小数点の強み（float は成り立たない）。

#### (4) 実際に使われている場所

| 領域 | フォーマット | 補足 |
|------|-------------|------|
| **Doom（1993）** | **16.16 固定小数点** | 当時の 386 に FPU が無かった。BSP ツリーも Doom が有名にした |
| Quake / 初期 3D | 16.16 | 同上 |
| 音声 DSP | Q1.15 / Q1.31 | `-1.0 〜 +1.0` に正規化。飽和演算が標準 |
| 画像処理 | Q8.8 / 8.8 固定 | α ブレンドなど |
| OpenGL ES 1.x | `GLfixed`（16.16） | FPU 無しの携帯端末向けプロファイル |
| 金額計算 | **10 進固定小数点**（×100 など） | 2 進固定小数点では 0.01 が厳密に表せないため、10 進スケールを使う |
| 対戦ゲームの lockstep 同期 | 実装依存 | プラットフォーム間のビット一致が必須 |
| 組込み制御 / PID | Q 形式各種 | FPU 無し MCU |

> **金額に 2 進固定小数点を使ってはいけない**理由: `0.01` は 2 進で循環小数。
> 1 円の誤差が積み上がる。正しくは「整数の銭単位」か 10 進固定小数点（`decimal` 型）。

### 4.7 幾何アルゴリズムの頑健性

#### (1) 外積は「正規化前の重心座標」である ★

まとめでは「外積や重心座標系を用いた」と並列に書かれているが、**この 2 つは同じもの**。

```text
  三角形 ABC と点 P について

  d1 = cross(B-A, P-A)   =  2 × (三角形 ABP の符号付き面積)
  d2 = cross(C-B, P-B)   =  2 × (三角形 BCP の符号付き面積)
  d3 = cross(A-C, P-C)   =  2 × (三角形 CAP の符号付き面積)

  重心座標:  λ_A = d2 / (d1+d2+d3)
             λ_B = d3 / (d1+d2+d3)
             λ_C = d1 / (d1+d2+d3)

  内側の条件:  λ が全部 0 より大きく 1 より小さい
            ⇔  d1, d2, d3 が全部同符号        ← 割り算が消える
```

**内外判定に必要なのは符号だけなので、正規化（割り算）を省ける。**
割り算を省くと、丸め誤差がゼロになり、しかも速くなる。

重心座標そのものが必要になるのは、**内部の値を補間したいとき**
（テクスチャ座標、頂点カラー、法線のグーロー／フォン補間）。ラスタライザはまさにこれをやっている。

#### (2) 幾何述語の頑健性（geometric robustness）

`orient2d`（3 点の向きを返す述語）は計算幾何学の基本演算で、
**符号を間違えるとアルゴリズム全体が破綻する**ことが知られている。

| 手法 | 厳密性 | 速度 |
|------|--------|------|
| `float` / `double` で素朴に計算 | ✗ ほぼ同一直線のとき符号が反転しうる | 速い |
| **整数で計算（本実装）** | ✅ 桁あふれしない範囲で完全に厳密 | 速い |
| 適応的高精度演算（Shewchuk の述語） | ✅ 完全 | 通常は速く、縮退時のみ遅い |
| 有理数 / 多倍長 | ✅ 完全 | 遅い |

Jonathan Shewchuk の *Adaptive Precision Floating-Point Arithmetic and Fast Robust
Geometric Predicates*（1997）は、この分野の標準文献。CGAL や Triangle が採用している。

**本課題の実装が整数演算なのは、偶然ではなく「最も頑健な選択肢を選んでいる」**という話ができる。

#### (3) 桁あふれの見積もり

```text
  座標の生値: 最大 2^31
  差分:       最大 2^32
  積:         最大 2^64        ← long（64bit）でも足りなくなりうる
```

厳密性を保証したいなら、**入力座標の範囲を契約として制限する**のが正しい設計。
例: 「座標は ±1024 の範囲」なら差分の生値は 2^19 以下、積は 2^38 以下で `long` に余裕で収まる。

#### (4) BSP の実体

**Binary Space Partitioning** = 空間を超平面（2D なら直線）で再帰的に二分し、木構造にする技法。

```text
        直線 L で空間を二分
              │
        ┌─────┴─────┐
      L の表側      L の裏側
        │             │
    さらに分割     さらに分割
```

| 用途 | 内容 |
|------|------|
| **可視性の順序付け** | Z バッファ無しで、視点から見て遠い順に描画できる（ペインターズアルゴリズム）。Doom が有名 |
| 衝突判定 | 点や球がどの領域にいるかを O(log n) で求める |
| CSG（立体の集合演算） | 和・積・差の計算 |
| レイトレーシングの加速 | kd 木は BSP の軸平行特殊形 |

**本課題で実装するのは「点が直線のどちら側か」という BSP の中核プリミティブだけ。**
木構造は作らない。「BSP という名前だけ借りている」ことを理解しておくと、
「BSP を実装したの？」と聞かれたときに正確に答えられる。

### 4.8 値オブジェクトと不変性の代償

#### (1) `const` メンバが奪うもの — そして no-op `operator=` が作る静かなバグ ★

C++98 の標準コンテナは、要素型に **CopyConstructible かつ Assignable** を要求する。
`const` メンバがあると代入ができないので Assignable を満たさない。

**ここからが重要で、`operator=` を「書くか書かないか」で結果がまったく変わる。**
以下は g++ 11.4 / `-std=c++98` で実際に確認した結果。

| ケース | `std::vector` に入れると | 危険度 |
|--------|------------------------|--------|
| **`operator=` を書かない**（暗黙宣言のまま） | 代入が必要な操作（`erase` など）で**コンパイルエラー**<br>`error: non-static const member 'const int X::_x', cannot use default assignment operator` | 安全（コンパイラが止めてくれる） |
| **no-op `operator=` を書く**（`Point` の実装） | **コンパイルが通り、実行もでき、結果だけが静かに壊れる** | **危険** |

```cpp
std::vector<Point> points;
points.push_back(Point(1.0f, 1.0f));
points.push_back(Point(2.0f, 2.0f));
points.push_back(Point(3.0f, 3.0f));   // ← push_back はコピー構築だけなので通る

points.erase(points.begin());          // ← 後続を「代入」で前へ詰める実装
```

実測結果:

```text
before:                 1 2 3
after erase(begin()):   1 2      ← size は 2 に減ったが、残ったのは 2 3 ではなく 1 2
expected:               2 3
```

**何が起きたか**: `erase` は要素を前へずらすときに `operator=` を使う。
`Point::operator=` は何もしないので、**ずらす処理だけが空振りし、末尾の 1 個が捨てられた**。
コンパイラは何も警告しない。テストが無ければ気づけない。

| 失われる能力 | 影響 |
|-------------|------|
| コピー代入の実体 | `operator=` が値を変更できない（OCF 要求と衝突） |
| ムーブ代入（C++11） | 同上 |
| `vector::erase` / `insert` / `resize` | **コンパイルは通るが結果が壊れる** |
| `std::sort` / `std::swap` | 同上（要素の入れ替えに代入を使うため） |

**設計上の教訓**:

1. **契約を満たせない操作を「何もしない実装」で黙らせると、コンパイルエラーが実行時バグに化ける。**
   エラーを消したのではなく、**発見を先送りした**だけ。
2. Module 02 では subject が `Fixed const` 属性と OCF の両方を要求しているので no-op を書くしかない。
   だが **ヘッダに「値は変わらない」と明記する義務**があり、それを怠ると他人を殺す。
3. 実務では次項の「private 非 const メンバ + const アクセサ」を選ぶ。

**Module 08 / 09 で STL を使うようになったとき、この話が効いてくる。**

#### (2) 不変性を保ちつつ代入可能にする設計

実務では `const` メンバではなく、**private な非 const メンバ + const アクセサのみ公開**で
不変性を表現する。

```cpp
class Point {
private:
    Fixed _x;                       // const を付けない
    Fixed _y;
public:
    Fixed const &getX() const;      // 読み取りしか公開しない
    Fixed const &getY() const;
    // setX / setY を作らない → 外からは不変に見える
};
```

| 方式 | 不変性 | 代入可能 | コンテナ可 |
|------|--------|---------|-----------|
| `const` メンバ | **言語が強制** | ✗ | ✗ |
| private 非 const + const アクセサ | 設計規約で保証 | ✅ | ✅ |

**Module 02 の subject は前者を明示要求している**ので今回は従う。
「後者が実務の標準で、その理由は STL 互換性」と言えることが到達点。

#### (3) 値オブジェクト（Value Object）とは

| 性質 | `Fixed` / `Point` の場合 |
|------|------------------------|
| **同一性ではなく等値性**で比較される | 「どの `Fixed` オブジェクトか」ではなく「値が同じか」 |
| 置き換え可能 | 同じ値のオブジェクトはどれと入れ替えても動作が変わらない |
| 状態機械ではない | 「注文中 → 発送済み」のような状態遷移を持たない |
| 副作用を持たない操作 | `a + b` は `a` も `b` も変えない |

これに対して **エンティティ（Entity）** は ID で同一性が決まる（同じ名前の別人は別人）。
DDD（ドメイン駆動設計）の基本的な区別で、`architecture.md` のドメインモデル監査で
`Fixed` を「値オブジェクト」と分類したのはこの意味。

### 4.9 テスト戦略

#### (1) テストの 3 階層

| 階層 | 内容 | 本課題での例 |
|------|------|-------------|
| **例示テスト** | 具体的な入出力の組 | `Fixed(42.42f).getRawBits() == 10860` |
| **性質テスト（property-based）** | **入力を変えても成り立つ法則**を検証 | `(a+b)-b == a` が任意の a, b で成立 |
| **ゴールデンファイル** | 出力全文を期待ファイルと `diff` | ex00 / ex01 の期待出力 |

**性質テストの価値**: 「たまたま通った」を排除できる。
`architecture.md` の T02-03（逆演算）、T03-13（頂点順序非依存）がこれにあたる。

#### (2) 検証すべき代数的性質

```text
  往復:        Fixed(x).toFloat()  ≈ x        （誤差 ≤ ε/2）
  単調性:      x < y  ⟹  Fixed(x) <= Fixed(y)
  単位元:      a + Fixed(0) == a,  a * Fixed(1) == a
  逆元:        (a + b) - b == a
  交換則:      a + b == b + a,  a * b == b * a
  結合則(加):  (a+b)+c == a+(b+c)
  結合則(乗):  成り立たない        ← 仕様として明記する
  符号:        (-a) * b == -(a * b)
```

#### (3) 境界値の選び方

| 分類 | 値 |
|------|-----|
| ゼロ近傍 | `0`, `+ε`, `-ε`, `-0.0f` |
| 1 近傍 | `1`, `1+ε`, `1-ε` |
| 符号の境界 | 正 / 負 / ゼロの全組合せ |
| 型の境界 | `INT_MAX`, `INT_MIN`, 値域の上限 `8388607.99609375` |
| 分解能の境界 | `ε/2`（丸めで消える）、`ε/2 + 微小`（残る） |
| 幾何の境界 | 頂点上、辺上、辺のすぐ内側／外側、退化三角形 |

### 4.10 ツールとコンパイラフラグ

## 8. 用語集

| 用語 | 意味 |
|------|------|
| OCF | Orthodox Canonical Form。42 の呼称。Rule of Three + デフォルトコンストラクタ |
| Rule of Three / Five / Zero | 特殊メンバ関数の実装指針（C++98 / C++11 / 現代） |
| アドホック多態性 | オーバーロードによる静的ディスパッチ |
| サブタイプ多態性 | 継承と仮想関数による動的ディスパッチ |
| パラメトリック多態性 | テンプレートによる型パラメータ化 |
| 生値 / raw bits | 固定小数点の内部整数表現 |
| Q 記法（Qm.n） | 整数部 m ビット・小数部 n ビットの固定小数点フォーマット |
| ε（イプシロン） | 表現可能な最小の刻み。本課題では 2^-8 = 0.00390625 |
| LSB | Least Significant Bit。誤差を「何 LSB」と数える |
| ULP | Unit in the Last Place。浮動小数点の刻み幅の単位 |
| 分解能 | 刻み幅。固定小数点では値域全体で一定 |
| ダイナミックレンジ | 表せる最大値と最小値の比。浮動小数点が優れる |
| UB | Undefined Behavior。規格が何も保証しない状態 |
| 処理系定義 | 実装が決めてよいが、文書化が必要な振る舞い |
| ODR | One Definition Rule。定義は 1 つだけという規則 |
| odr-used | 値だけでなく「実体」が必要になる使われ方。定義が要る |
| コピー省略 / RVO / NRVO | 一時オブジェクトのコピーを省く最適化 |
| Most Vexing Parse | `Fixed a();` が関数宣言になる C++ の構文上の罠 |
| ADL | 引数依存名前探索。非メンバ演算子が見つかる仕組み |
| 狭義弱順序 | `std::sort` / `std::map` が `operator<` に要求する性質 |
| Assignable | C++98 の STL コンテナが要素型に要求する「代入可能」要件 |
| 値オブジェクト | ID ではなく値で同一性が決まる型 |
| 飽和演算 | 桁あふれ時に折り返さず上限・下限で止める演算 |
| 銀行家の丸め | 最近接偶数丸め。IEEE 754 の既定 |
| FMA 縮約 | `a*b+c` を 1 命令にまとめる最適化。丸め回数が変わる |
| 外積（2D） | `u.x*v.y - u.y*v.x`。符号で左右、絶対値で面積 |
| 重心座標 | 三角形内の点を 3 頂点の重み付き和で表す座標系 |
| BSP | Binary Space Partitioning。超平面による空間の再帰二分割 |
| 幾何述語 | `orient2d` など、符号だけを返す基本演算 |
