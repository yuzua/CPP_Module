## 1. 設計の進め方 — mino skill suite の当て方

再現性の定義は「毎回同じコードになること」ではない。
**実装が違っても、同じ問題・契約・モデル・公開境界を満たせること** である。

成果物が設計文書と参考実装の両方なので、入口は `mino-reproducible-development`。
中身は専門 Skill に分解した。`mino-core` は共通規則の基盤であり、単独では使わない。

| Skill | 何を強制するか | このモジュールでの使い所 |
|-------|----------------|--------------------------|
| `mino-problem-framing` | 技術語を消しても問題が残るように書く。手段は候補に戻す | 「virtual を使え」を「**窓口の型が基底のままでも、振る舞いは実体のもの**」に戻す（3章） |
| `mino-domain-model-completeness` | 用語、状態、失敗、writer / reader、authority の穴を監査する。表が埋まったことを完成と呼ばない | `type` の意味、`Brain*` の持ち主、床に置いたマテリア（5章） |
| `mino-design-by-contract` | 事前条件 / 事後条件 / 不変条件 / 失敗後の状態 / そのテスト | `makeSound`、`equip`、`unequip`、`learnMateria`（7〜10章） |
| `mino-interface-implementation-separation` | 利用者が知る意味と、vtable や `new` の手順を分ける。if の個数を品質にしない | `Character` が `Ice` を知らないこと（6章、10章） |
| `mino-architecture-quality-strategy` | 全品質を同時に最大化しない。順位と犠牲を先に書く | 仕様適合 > 所有権の単一性 > 説明可能性（4.3） |

各 ex の説明順は、そのまま defense の説明順になる。

```text
  ① 問題（何が困るか。virtual という言葉を使わずに）
  ② モデル（概念、不正な状態、誰が書くか）
  ③ 契約（成功したら何が真か。失敗したら何が残るか）
  ④ 境界（hpp に出すもの、出さないもの）
  ⑤ 案 A/B/C と、採用理由
  ⑥ 契約を破る実装を落とすテスト
```

Skill の Hard Gate を、この課題の自分ルールに読み替えた。

| Hard Gate | この課題での読み替え |
|-----------|----------------------|
| 技術語を除くと問題が消えるなら、問題が書けていない | 「vtable を学ぶ」は目的ではない。問題は 3章の文 |
| if 数・interface 数を品質にしない | `ICharacter` を作ったこと自体は偉くない。**Character の分岐が増えずに Fire を足せること**が品質 |
| 表が埋まったことを model complete にしない | コンパイル成功では完成にしない。**浅いコピーと、基底ポインタの delete** をテストして初めて完成 |
| N/A には理由、unknown には確認方法 | 「ex03 の構築メッセージを出さない」は、提示 main の期待出力が根拠 |
| 共通化は目的・契約・変更理由が揃うときだけ | `Dog` と `Cat` の Brain 処理は似ている。それでも中間クラスは作らない（8.4） |
| 公開契約の最終判断は人間が持つ | `learnMateria` の「コピー」の読みは課題文が二義的。採用した契約を文書に残す（10.2） |
| 全品質の最大化をしない | 例外安全なコピー（Module 05）は今回やらない、と先に書く |

## 2. 良い設計とは何か

### 2.1 この課題で使う定義

| # | 定義 | この課題での具体 |
|---|------|------------------|
| 1 | **問題と手段を混ぜない** | `virtual` は手段。問題は「呼び手が実体のクラス名を知らなくても、正しい処理と正しい破棄が起きる」 |
| 2 | **不正な状態を、公開操作から作れない** | 1 個の `new` に `delete` の責任者が 2 人いる状態を、`equip` もコピーも作らない |
| 3 | **不変条件の owner が一人** | 「この `Brain` を消すのはこの `Dog`」を `Dog` 以外が持たない |
| 4 | **失敗したあとの状態を言える** | 満杯の `equip` は何も受け取らない。渡したポインタは呼び出し側がまだ持っている |
| 5 | **利用者が知る意味と、内部手順を分ける** | `main` は `use(0, bob)` を呼ぶ。スロットが `Ice` かは見ない |
| 6 | **違う実装でも同じ契約なら同じ設計** | 鳴き声の英文が違っても、「基底ポインタ経由で派生の鳴き声になる」契約は同じ |
| 7 | **説明できる** | 「なぜ `getType()` は virtual ではないのに動くのか」を、データと関数本体の違いで言える |

### 2.2 きれいと良いは違う

```text
  きれい（見た目）
    クラスが少ない / 行が短い / Dog と Cat をマクロでまとめた / vector で床を掃いた

  良い（検証できる）
    virtual を外すとテストが落ちる
    コピーの片方だけアイデアを変えても、もう片方は変わらない
    Character.cpp を開かずに Fire を足せる
```

`protected` の `type` に派生のあちこちから代入するのは短い。
コンストラクタ引数に寄せる方が数行増える。増える方が良い。
Skill が「if の個数を品質にするな」と言うのは、この区別のため。

### 2.3 Module 03 との違い

Module 03 の良い設計は「戦闘ルールの owner を `ClapTrap` 一人にする」だった。
属性を `protected` に開けない、という判断が中心だった。

Module 04 では課題が **`type` を protected と指定している**。
同じ「private にせよ」を持ち込むと、課題の文言に反する。
こちらでの良い設計は次の二つに移る。

1. **指定された protected は守る。** そのうえで、書き込む場所をコンストラクタに限る。
2. **`new` の owner を一人にする。** `virtual` デストラクタは、その owner の破棄関数が実際に呼ばれるための条件。

## 3. Problem Frame

技術語を外した問題。

| 項目 | 内容 | 根拠 |
|------|------|------|
| **観測** | 動物の種類、魔法の種類は増える。呼び手は「動物」「マテリア」「キャラクター」としか書きたくない | subject の main。`Animal*` と `AMateria*` |
| **誰が困るか** | 種類を足すたびに `if (dog) ... else if (cat)` を直す人。消し忘れで `Brain` が残る人 | ex00 の Wrong 実験、ex01 の delete、ex03 の「インベントリはあらゆる AMateria」 |
| **目的** | 窓口の型を固定したまま、**鳴き声・破棄・複製・使用の中身を実体側に置く** | subject の各章を横断した目的 |
| **成功条件** | ① 基底ポインタの `makeSound` が実体の鳴き声 ② `delete` で派生デストラクタが先 ③ コピーは別 `Brain` / 別マテリア ④ `Animal` を ex02 で作れない ⑤ 提示 main の 2 行 ⑥ `Character` が `Ice` に依存しない | subject + 本書の契約 |
| **拒否条件** | `dynamic_cast` で種類を分岐する。`std::vector` で床を実装する。ex03 のクラスが構築メッセージを出して提示出力を壊す。浅いコピーのまま「動いた」と言う | 一般規則、提示出力、知識としての RTTI |
| **候補手段** | virtual 関数、純粋仮想、`clone()`、ポインタの所有移譲 | 7〜10章で比較 |
| **未決だったもの** | `learnMateria` がポインタを受け取るのか、中で clone するのか。本書 10.2 で決めた | 課題文の「コピー」と、提示 main がアドレスを保持しないことの両方 |

「virtual を付けろ」は手段である。
defense では「窓口が `Animal*` のままで、犬は犬の鳴き声を出す。種類を足しても窓口の if を増やさない」と言う。

### 3.1 候補手段（モジュール全体）

| 手段 | 何が起きるか | 採用 |
|------|--------------|------|
| **基底ポインタ + virtual** | 呼び手は基底だけを書く。実体が関数を選ぶ | **採用** |
| 呼び手の if / switch | 動く。新しい種類のたびに呼び手を修正する | 拒否。ex03 の `Fire` 追加で `Character` を開くことになる |
| `dynamic_cast` でダウンキャスト | 動く。種類の知識が呼び手に戻る | 拒否。Module 06 の道具であり、このモジュールの目的と逆 |
| 値の配列 `Animal zoo[4]` | スライスする。ex02 ではコンパイルできない | 拒否。ポインタの配列にする |

## 4. モジュール全体の方針

### 4.1 D-00: 演習ディレクトリの置き方

| 案 | 内容 | 利点 | 欠点 |
|----|------|------|------|
| **A（推奨）** | ex00 を完成させてから ex01 にコピーし、差分だけ足す。ex03 は別プログラム | 各ディレクトリが、その章の課題ちょうどになる | コピー漏れ |
| B | 最初から ex03 の完成形を書き、前の章用に削る | 手戻りが少ない | ex00 に `Brain` や純粋仮想が混ざり、「課題を読んでいない」と見える |
| C | ヘッダを symlink で共有 | 重複が消える | 提出物としてディレクトリが単体で完結しない |

**推奨は A。** コピー直後にやること:

```text
ex00 → ex01:  Dog と Cat に Brain* を足す。Animal の virtual はそのまま使う
ex01 → ex02:  makeSound を純粋仮想にする。new Animal() を消す
ex03:         Animal を持っていかない。マテリアのプログラムを新規に書く
```

### 4.2 D-01: ログ

| 範囲 | 方針 | 理由 |
|------|------|------|
| ex00〜ex02 | 構築 / コピー構築 / 代入 / 破棄を、クラス名から始まる別々の文で `std::cout` に出す | 課題が「クラスごとに違うメッセージ」と要求している。順序のテストがこの文を探す |
| ex03 | **クラスは何も出さない。** 出すのは `use()` の課題文だけ | 提示 main の期待出力が 2 行だけ。構築ログを出すと、その main を貼ったときに一致しない |
| テストの見出し | `main` が出してよい | 「提示以上のテスト」は main の責務。クラスの責務ではない |

鳴き声の英文は課題が固定していない。参考実装は次で固定し、テストは **文面の一致ではなく、誰の音か** を比べる。

| クラス | `makeSound` |
|--------|-------------|
| `Animal` | `Animal makes no particular sound.` |
| `Dog` | `Dog barks: Woof` |
| `Cat` | `Cat meows: Meow` |
| `WrongAnimal` | `WrongAnimal makes a generic wrong sound.` |
| `WrongCat` | `WrongCat hisses: Meow` |

猫の文に `Woof` を入れない。課題の「猫は吠えない」。

ex03 の `use` だけは空白まで固定する。

```text
* shoots an ice bolt at bob *
* heals bob's wounds *
```

### 4.3 品質の優先順位

| 順位 | 品質 | 理由 | 犠牲にするもの |
|------|------|------|----------------|
| 1 | **仕様適合** | 評価の合否。virtual、純粋仮想、深いコピー、提示 2 行、OCF、C++98 | — |
| 2 | **`new` の owner が一人** | リークと二重解放は、このモジュールの失敗の本体 | 短い浅いコピー |
| 3 | **説明可能性** | 課題の AI 章。評価は口頭 | CRTP、独自の RTTI、床の自動 GC |
| 4（制約） | `-Wall -Wextra -Werror -std=c++98`、STL コンテナ禁止 | 妥協しない | `override`、`nullptr`、`std::vector` |
| 5（意図的にやらない） | 例外安全なコピー | `new` が失敗した途中状態は Module 05 の主題 | try/catch、コピーを先に作ってから入れ替える強い保証 |

5 をやらない、と先に書いておく。
代入は「自分のマテリアを消してから `clone` する」。
`clone` の途中で `std::bad_alloc` になると、消した分は戻らない。
この課題の入力では `new` は成功する前提で、**自己代入で自分を消さないこと**までを保証する。

## 5. ドメインモデル

固定するユースケースは二つ。

1. **動物**: 作り、基底の窓口から鳴かせ、コピーし、基底の窓口から消す。
2. **マテリア**: 見本を覚え、名前で複製し、キャラクターに持たせ、使い、外し、キャラクターごと消す。

### 5.1 用語

| 用語 | 意味 | 反例（この課題ではそう呼ばない） |
|------|------|----------------------------------|
| 種類名 `type` | その個体がどの種類かの文字列。`"Dog"`、`"ice"` | クラス名 `Ice` と文字列 `"ice"` は別物 |
| 鳴き声 | `makeSound` が標準出力に書く処理 | `type` に入っているデータではない |
| 脳 | `Dog` または `Cat` が 1 個所有する `Brain`。アイデア 100 個 | `Animal` は脳を持たない |
| 見本 | `MateriaSource` が覚えているマテリア | `createMateria` が返す個体そのものではない |
| 装備 | `Character` のスロットが指しているマテリア | 床に置いたあとのマテリアは装備ではない |
| 床 | `unequip` したあと、呼び出し側がアドレスを持っている状態 | クラスとしては作らない（10.4） |

### 5.2 12 観点

| 観点 | 処遇 | 根拠 |
|------|------|------|
| term_context | present | 上の表。`"Ice"` と `"ice"` を混ぜない |
| concept | present | 動物、脳、マテリア、見本、装備 |
| constraint | present | アイデア添字は 0〜99。スロットは 4。`type` は構築時に決まる |
| state | present | スロットは空か、マテリアを所有しているか |
| transition | present | equip で空→所有。unequip で所有→呼び出し側へ戻る |
| behavior | present | makeSound / clone / use / equip / unequip / learn / create |
| relationship | present | Dog is-a Animal。Ice is-a AMateria。Character is-a ICharacter。Dog has-a Brain |
| failure | present | 範囲外、空スロット、未知タイプ、満杯。状態を壊さない |
| time | N/A | クールダウンも期限も課題に無い |
| writer | present | コンストラクタ、代入、equip、unequip、learn、setIdea |
| reader | present | getType、getIdea、getName、makeSound、use の出力 |
| authority | present | 鳴き声の中身は派生。Brain の delete は Dog/Cat。装備の delete は Character。見本の delete は MateriaSource |

画面が埋まったことは、完成ではない。5.3 の入力で writer を壊しにいって、初めて監査になる。

### 5.3 壊しにいく入力

| 入力 | 守るべきこと | よくある壊れ方 |
|------|--------------|----------------|
| `Animal* p = new Dog(); p->makeSound()` | 犬の鳴き声 | virtual 忘れ、または const の不一致 |
| `delete p` | `~Dog` が `~Brain` より先、そのあと `~Animal` | デストラクタが非 virtual |
| `Dog` をコピーして、コピーのアイデアだけ変える | 元のアイデアは変わらない | `brain_(other.brain_)` |
| `new Animal()` を ex02 に残す | コンパイルエラー | 純粋仮想にしていない |
| `AMateria&` 経由で Ice に Cure を代入 | Ice の type は `"ice"` のまま | `operator=` が type をコピーする |
| 満杯の `equip` | 渡したポインタは生きている。呼び出し側が delete できる | equip が中で delete した |
| `unequip` したポインタを delete | 二重解放しない。use は無音 | unequip が delete した、または equip が別 clone を保持した |
| `learnMateria(new Ice())` を 5 回 | プロセスがリークしない | 5 個目のアドレスを捨てて delete しない |
| キャラクターをコピーし、元だけ破棄 | コピーの `use` がまだ鳴る | スロットが同じポインタを共有 |

アイデアの独立性を見るテストは CI-12。キャラクターのコピーを見るテストは CI-37。

### 5.4 不変条件

| ID | 条件 | owner |
|----|------|-------|
| INV1 | 構築完了後の `Animal::type` は、派生が初期化子で渡した種類名 | 初期値は派生の初期化子。保管は `Animal` |
| INV2 | `makeSound` はオブジェクトの状態を変えない | 各動物 |
| INV3 | `Dog` / `Cat` は、生存中ちょうど 1 個の `Brain` を所有する | `Dog` / `Cat` |
| INV4 | その `Brain` を `delete` するのは、その犬または猫のデストラクタだけ | `Dog` / `Cat` |
| INV5 | `AMateria::type` は構築時に決まり、代入では変わらない | `AMateria` |
| INV6 | キャラクターの各スロットは、空か、他人と共有しないマテリア 1 個 | `Character` |
| INV7 | 見本スロットも同じ。`createMateria` は見本とは別の個体を返す | `MateriaSource` |

INV1 は **完全には型で守れない**。`type` が protected なので、派生が後から代入すれば破れる。
参考実装にはその代入が無い。課題が private を許さないので、ここは「書かない」という規律であり、コンパイラの強制ではない。defense ではその限界を先に言う。

## 6. 公開境界

### 6.1 誰が何を知るか

| 利用者 | 知ってよい | 知らなくてよい |
|--------|------------|----------------|
| ex00 の main | 作る、`getType`、`makeSound`、基底ポインタで消す | vtable の何番目か |
| ex01 の main | アイデアを読み書きする、コピーが独立していること | `Brain*` のアドレス |
| ex03 の main | 覚える、作る、装備する、外す、使う、消す | スロット配列の中身、`Ice` というクラスを `Character` が include しているか |
| 評価者 | 上の契約と、破棄の順序 | テスト用ヘルパの実装 |

### 6.2 D-02: `type` をどこに置くか

課題は「protected な `std::string type`」と書いている。Module 03 の「データは private」をそのまま適用すると、課題違反になる。

| 案 | 内容 | 利点 | 欠点 |
|----|------|------|------|
| A | protected のまま、派生の本体で `this->type = "Dog"` | 課題の文に一番近い。短い | 構築後にも書ける。書き込み箇所が本体に散る |
| **B（推奨）** | **属性は protected のまま。設定は `Animal` の protected コンストラクタ引数だけ** | 派生は `Animal("Dog")` と書く。構築後の本体に代入が残らない | 派生が意地でも `type = ` と書けば INV1 は破れる（5.4） |
| C | private にして protected の setter を出す | カプセル化としては一番強い | **課題が protected 属性を指定しているのに反する** |

**推奨は B。** defense の言い方:

> 属性の可視性は課題どおり protected です。
> 変えたのは可視性ではなく、書き込むタイミングです。
> 派生は種類名を初期化子で渡し、`Animal` がメンバを初期化します。

`getType()` は const で、参照を返す。virtual にはしない（7.3）。

### 6.3 D-03: テストのためにどこまで開くか

| 案 | 内容 | 判定 |
|----|------|------|
| A | getter を出さず、cout の目視だけ | 契約を破ってもテストが赤くならない |
| **B（推奨）** | `getType` / `getIdea` / `getName` だけ公開する。`Brain*` は出さない | アイデアの独立性は文字列で判定できる。アドレスは実装の観測 |
| C | `getBrain()` や `getSlot()` を公開する | テストがポインタの共有という実装に依存する。所有権の境界がテスト側に漏れる |

`Brain` の配列 `ideas` は private。読み書きは `setIdea` / `getIdea`。
範囲外は状態を変えない。

`Character` にスロットの getter は付けない。
深いコピーの証拠は「元を破棄したあとも、コピーの `use` が鳴る」こと。
ポインタが同じなら、元のデストラクタが消したあとコピーは使えない。

### 6.4 この課題に無い意味

| 項目 | 判定 | 理由 |
|------|------|------|
| リトライ | N/A | 失敗した `equip` は状態を変えない。呼び出し側がもう一度呼ぶかどうかは課題の外 |
| タイムアウト | N/A | 同期・単一スレッド |
| 冪等性キー | N/A | 永続化もネットワークも無い。同じマテリアを 2 回 `equip` したときの扱いは 10.6 で別契約にする |

## 7. ex00 — ポリモーフィズム

### 7.1 問題

`const Animal*` に犬が入っているとき、鳴く関数は犬のものか。
同時に、同じ形なのに virtual が無いと基底の鳴き声になる、を隣に置く。

### 7.2 D-04: `makeSound` の形

| 案 | 内容 | 判定 |
|----|------|------|
| A | 非 const、非 virtual | 課題の `const Animal*` がコンパイルできない。鳴き声も基底に固定される |
| B | virtual、非 const | 課題の main がコンパイルできない |
| **C（推奨）** | **`virtual void makeSound(void) const`** | 課題のポインタから呼べる。動的な型の関数が選ばれる |
| D | 派生だけ virtual | 基底が virtual でなければ、基底ポインタからの呼び出しは静的束縛のまま |

**推奨は C。** const は「鳴いても状態が変わらない」（INV2）でもある。

### 7.3 D-05: `getType` を virtual にするか

| 案 | 内容 | 判定 |
|----|------|------|
| **A（推奨）** | 非 virtual。メンバ `type` を返す | 違いはデータに入っている。基底の関数がそれを読むだけで課題の main が成立する |
| B | virtual にして派生が `"Dog"` を返す | 動く。ただし `type` メンバを課題が置いた理由が消える |

**推奨は A。** Wrong 実験の説明がこれで一箇所に決まる。

> `WrongAnimal*` でも `getType()` は `"WrongCat"` になりうる。データは実体のものだから。
> `makeSound()` は `WrongAnimal` の文になる。選ばれる関数本体が、ポインタに書いた型のものだから。

テスト CI-07 がこの対比を機械的に見る。

### 7.4 D-06: Wrong 側で何を非 virtual にするか

| 案 | 内容 | 判定 |
|----|------|------|
| A | `makeSound` もデストラクタも非 virtual | 鳴き声の対比は出る。`delete` が未定義動作になる |
| **B（推奨）** | **`makeSound` だけ非 virtual。デストラクタは virtual** | 見せたい差は鳴き声。破棄は定義された動作のままテストできる |
| C | 両方 virtual | Wrong 実験にならない |

**推奨は B。**

### 7.5 D-07: デストラクタ

`Animal` と `WrongAnimal` のデストラクタは public virtual。
課題の main には `delete` が無い。提出テストでは `delete` する。
そのテストを未定義動作にしないために、ex00 の時点で virtual にする。
ex01 で思い出す順序だと、ex00 のテストがすでに危険になる。

### 7.6 契約（ex00）

| ID | 操作 | 成功時 | 失敗の置き場 |
|----|------|--------|--------------|
| CI-01 | `Animal*` 経由の `getType` | 犬は `"Dog"`、猫は `"Cat"`、素の Animal は `"Animal"` | — |
| CI-02 | `Animal*` 経由の `makeSound` | 犬の音は、素の Animal の音と違う。猫の音は犬の音と違う。具体的な `Dog` 変数の音と、`Animal*` 経由の音は同じ | virtual を外すと犬と Animal の音が一致し、テストが落ちる |
| CI-03 | `WrongAnimal*` 経由の `makeSound` | `WrongAnimal` の音と一致する。具体的な `WrongCat` の音とは一致しない | virtual を付けてしまうと、この一致が壊れてテストが落ちる |
| CI-04 | `Animal*` の `delete` | ログ上、`Dog is destructed.` が `Animal is destructed.` より前 | 非 virtual だと犬の行が出ない |
| CI-05 | `Dog` のコピー | `getType()` が `"Dog"` | コピーコンストラクタが `Animal(other)` を忘れると空や `"Animal"` になる |
| CI-06 | 値へのコピー `Animal sliced = dog` | 音は Animal のもの | スライスを検出する。ex02 ではこの行自体が書けなくなるのでテストから外す |
| CI-07 | `WrongAnimal*` の `getType` と `makeSound` | type は `"WrongCat"`、音は WrongAnimal | データと関数本体を取り違えた説明を落とす |

### 7.7 公開面の骨格

```cpp
class Animal {

        Animal(void);
        Animal(Animal const &other);
        virtual ~Animal(void);
        Animal &operator=(Animal const &other);

        std::string const &getType(void) const;
        virtual void makeSound(void) const;

```

`Dog` は `Animal("Dog")` だけを呼ぶ。本体で `type` に代入しない。`Cat` も同じ。

## 8. ex01 — Brain と深いコピー

### 8.1 問題

犬を `Animal*` として消しても、その犬が `new` した脳が残らない。
コピーした犬のアイデアを変えても、元の犬のアイデアは変わらない。

### 8.2 D-08: `Brain` の持ち方

| 案 | 内容 | 判定 |
|----|------|------|
| A | `Brain brain;` を値メンバにする | `std::string` のコピーが自動で深い。課題が `new Brain()` と書いているのに反する |
| **B（推奨）** | **`Brain* brain_` を構築で `new`、破棄で `delete`** | 課題どおり。所有権を自分で書く演習になる |
| C | 犬と猫で 1 個の脳を共有 | 課題の「自身の Brain」に反する。破棄が二重解放になる |

**推奨は B。** メンバ名は `brain_`。課題は型が `Brain*` であることだけを指定していて、識別子は指定していない。`ideas` と `type` は課題が名前を書いているので、その綴りを使う。

### 8.3 D-09: 深いコピーの書き方

| 案 | 内容 | 利点 | 欠点 |
|----|------|------|------|
| A | `delete brain_; brain_ = new Brain(*other.brain_);` | 分かりやすい | 自己代入で自分を消してから自分を読む。`new` が失敗するとポインタが宙ぶらりん（今回は 4.3 の範囲外だが、自己代入は範囲内） |
| **B（推奨）** | **`*brain_ = *other.brain_`** | 既存の脳に 100 文字列をコピーする。確保し直さない。自己代入チェックと相性が良い | `Brain` の代入が正しいことが前提 |
| C | Copy-and-Swap | 例外安全の定石 | C++98 の `std::swap` は `<algorithm>` にあり、Module 08 まで禁止。コピーのログも増える |

**推奨は B。** 自己代入は先に `return` する。

```cpp
Dog &Dog::operator=(Dog const &other) {
    if (this != &other) {
        Animal::operator=(other);
        *this->brain_ = *other.brain_;
    }
    std::cout << "Dog is copy-assigned." << std::endl;
    return *this;
}
```

コピーコンストラクタは新しく確保する。代入と違い、こちらはまだ脳を持っていない。

```cpp
Dog::Dog(Dog const &other)
    : Animal(other), brain_(new Brain(*other.brain_)) {}
```

`Animal(other)` を省くと、`type` が `"Dog"` にならない（CI-05 が ex01 でも生きている）。

### 8.4 D-10: Dog と Cat の重複を消すか

| 案 | 内容 | 判定 |
|----|------|------|
| A | `BrainOwner` のような中間クラスに `brain_` を上げる | 行数は減る。課題に無い階層が増える。評価者が追う型が増える |
| B | マクロで特殊関数を生成 | 読めない |
| **C（推奨）** | **Dog と Cat に同じ形をそれぞれ書く** | 目的は同じでも、課題は二つの具象クラスとして読ませる。説明可能性を優先する |

Skill の「共通化は目的・契約・変更理由が揃うときだけ」。
三つは揃っているようにも見える。それでも C にする理由は、品質順位の 3（説明可能性）が、行数の削減より上だから。4.3 で先にそう決めた。

### 8.5 契約（ex01 で足すもの）

| ID | 成功時に真であること |
|----|----------------------|
| CI-10 | `delete` した犬 1 匹につき、ログは `Dog is destructed.` → `Brain is destructed.` → `Animal is destructed.` |
| CI-11 | 4 匹の配列（犬 2、猫 2）を `Animal*` で消すと、犬の破棄 2、猫の破棄 2、脳の破棄 4、Animal の破棄 4 |
| CI-12 | コピー構築のあと、コピーのアイデア 0 を変えても元は変わらない |
| CI-13 | 代入でも同じ |
| CI-14 | 自己代入のあと、アイデアが残っている |
| CI-15 | `setIdea(-1)` と `setIdea(100)` は、既存のアイデア 0 を変えない |
| CI-16 | CI-12 を猫でも行う |

アドレス比較はしない。CI-12 が落ちる実装は浅いコピーである。

## 9. ex02 — 抽象クラス

「ただの動物」をオブジェクトとして作れなくする。
犬と猫の使われ方は ex01 のまま。

### 9.2 D-11: インスタンス化をどう止めるか

| 案 | 内容 | 判定 |

| A | コンストラクタを protected にするだけ | 外からは作れない。**抽象クラスではない**。派生のメンバ関数からは作れる。値スライスの宣言も、コンストラクタが protected なら外部からは書けないが、規格上の抽象クラスではない |

犬、猫、脳、深いコピーの契約は ex01 と同じ結果。

## 10. ex03 — インターフェースと所有権

### 10.1 問題

キャラクターは、氷か治療かをソース上で知らなくても、スロットのものを使える。
新しい魔法を足すときに、キャラクターのファイルを開かない。
そのために生まれる `new` のそれぞれについて、誰が `delete` するかが一人に決まる。

`Animal` 一式は持っていかない。課題の提出ファイルリストが、前の演習のファイルを含んでいない。

### 10.2 D-12: `learnMateria` は何を受け取るか

課題は「コピーして保存」と書く。提示 main は `learnMateria(new Ice())` と書き、そのアドレスを変数に残さない。

| 案 | 契約 | 提示 main | 呼び出し側がアドレスを持っていた場合 |
|----|------|-----------|--------------------------------------|
| A | 中で `clone` し、引数は呼び出し側のまま | **リークする**。main が delete しない | 引数は有効なまま |
| B | 中で `clone` し、引数をその場で `delete` | リークしない | **戻ったあと引数は無効。** 呼び出し側からは見えない |
| **C（推奨）** | **渡されたポインタを見本としてそのまま保持する。複製は `createMateria` の `clone()` が行う** | リークしない。`delete src` が見本を消す | 呼んだあと、そのアドレスの delete は MateriaSource が行う。呼び出し側は消さない |

**推奨は C。** 「コピー」という言葉は、見本から複製を作る責務が `createMateria` 側にある、と読んだ。
A は課題の main をリークさせる。B は「コピー」に字面は近いが、渡したポインタが黙って無効になる。

defense ではこう言う。

> 提示 main は `new` のアドレスを保持しません。
> だから所有権は `learnMateria` に移ると決めました。
> 複製を作るのは、タイプ文字列だけを受け取る `createMateria` です。

これは課題文の一つの読みであり、A を「字面どおり」と主張する評価者はいる。
そのときは上の二文で、リークしない方を選んだ理由を言う。実装を黙って両方やらない。

満杯、または保存できないときの C の続き:

| 状況 | すること |
|------|----------|
| 引数が 0 | 何もしない |
| すでに同じアドレスを保持している | 何もしない。delete しない（もう自分が持っている） |
| 空きがある | そのポインタを空きに入れる |
| 空きが無い | **`delete` する。** 所有権は呼んだ瞬間に移っているので、捨てるとリークが確定する |

`equip` の満杯はこれと違う。10.3。

### 10.3 D-13: `equip` は clone するか

| 案 | 内容 | 判定 |
|----|------|------|
| **A（推奨）** | **渡されたポインタを、最初の空きスロットにそのまま入れる** | `unequip` のあと、呼び出し側が元のアドレスを `delete` できる。課題の「先にアドレスを保存せよ」と一致する |
| B | 中で `clone` し、引数を `delete` | 提示 main はリークしない。ただし unequip 後に手元のポインタを消すと二重解放か、すでに無効 |
| C | 中で `clone` し、引数は放置 | 提示 main の `tmp` がリークする |

**推奨は A。**

失敗したとき:

| 状況 | すること | 失敗後の持ち主 |
|------|----------|----------------|
| 引数が 0 | 何もしない | 誰も `new` していない |
| 同じアドレスが既に入っている | 何もしない。delete しない | 1 回目の `equip` で Character が持ったまま |
| 空きが無い | 何もしない。**delete しない** | **呼び出し側**。課題は「何も起きない」と書いている。main は `tmp` をまだ持っている |

`learnMateria` と `equip` で、満杯時の delete が違う。
違いは気紛れではない。**提示コードが、アドレスを変数に残すかどうか**が違う。

```text
  learnMateria(new Ice())     アドレスを捨てる  → 受け手が最後まで責任を持つ
  tmp = create...; equip(tmp) アドレスが残る    → 受け取れなかったものは tmp のまま
```

### 10.4 D-14: 床をクラスにするか

| 案 | 内容 | 判定 |
|----|------|------|
| **A（推奨）** | **床クラスを作らない。** `unequip` はスロットを 0 にするだけ。テストが、equip に渡したポインタをあとで `delete` する | 課題の文「呼ぶ前にアドレスを保存せよ」そのもの |
| B | 固定長配列の `Floor` が後でまとめて消す | 動く。課題が要求していない仕組みが増える。STL を使わずに書く必要がある |
| C | `std::vector` に落とす | **Module 08 まで禁止。大幅減点** |

**推奨は A。** `unequip` はマテリアを `delete` しない、は課題が明示している。

### 10.5 D-15: 代入と `type`

| 対象 | 代入で `type` をコピーするか | 理由 |
|------|------------------------------|------|
| `Animal` | **する** | コピーした犬は犬のままである、が契約（CI-05） |
| `AMateria` | **しない** | 課題が明示。Ice に Cure を基底参照で代入しても、Ice の type は `"ice"` のまま（CI-32） |

コピー**コンストラクタ**はどちらも type をコピーする。
禁止されているのは代入の方。`clone()` はコピーコンストラクタ経由なので、新しい Ice の type は `"ice"` になる。

```cpp
AMateria &AMateria::operator=(AMateria const &) {
    return *this;
}
```

引数に名前を付けない。`-Wextra` が未使用引数をエラーにするため。中で `type` を触らない。

### 10.6 D-16: 同じポインタを二度 equip する

課題は書いていない。書かないと、二つのスロットが同じアドレスを持ち、デストラクタが二度 `delete` する。

| 案 | 内容 | 判定 |
|----|------|------|
| A | 何も検査しない | 二重解放が残る |
| **B（推奨）** | **同じアドレスが既にあれば、2 回目は何もしない** | INV6（共有しない）を公開操作が破れなくなる |
| C | 2 回目も別スロットに入れる | 課題の「最大 4 個」には合う。破棄が未定義動作 |

**推奨は B。** 2 回目は失敗であり、1 回目の所有はそのまま。

### 10.7 D-17: キャラクターのコピー

課題: コピーは深い。持っていたマテリアは、新しいものを入れる前に消す。破棄時にも消す。

| 案 | 内容 | 判定 |
|----|------|------|
| A | ポインタをコピーする | 浅い。両方のデストラクタが同じものを消す |
| **B（推奨）** | **自己代入なら何もしない。そうでなければ全部 `delete` してから、相手の各要素を `clone()` する** | 課題の「先に消してから入れる」と一致する。自己代入で自分を消してから読まない |
| C | 先に全部 `clone` して一時配列へ入れ、そのあと入れ替える | 例外安全は上。4.3 で今回はやらないと決めた。自己代入ガード付きの B で契約は識別できる |

コピー構築には、消すべき古いマテリアが無い。
スロットを先に 0 にしてから `clone` する。未初期化ポインタを `delete` しない。

`MateriaSource` も同じ形にする。
課題が「深い」と書いたのは `Character` だけである。
`MateriaSource` に同じことをする理由は、見本ポインタを所有しているから（Rule of Three、INV7）。
浅いコピーのまま二つ破棄すると二重解放になる。

### 10.8 D-18: `Character` は具象マテリアを知らない

| 案 | 内容 | 判定 |
|----|------|------|
| A | `use` の中で `type == "ice"` なら氷の文、と書く | 提示 main は動く。`Fire` を足すたびに `Character.cpp` を開く |
| **B（推奨）** | **`inventory_[idx]->use(target)` とだけ書く** | 文面の owner は `Ice` と `Cure`。`Character.hpp` は `AMateria` を前方宣言するだけ |

**推奨は B.** `Ice.hpp` を `Character.hpp` からも `Character.cpp` からも include しない。
評価中に `Fire` を頼まれたら、足すファイルは `Fire.hpp`、`Fire.cpp`、`main.cpp`、Makefile のソース一覧。`Character.cpp` は開かない。

`use` という名前が二つある。

| 関数 | 意味 |
|------|------|
| `Character::use(int, ICharacter&)` | 何番を、誰に対して使うか。空なら何もしない |
| `AMateria::use(ICharacter&)` | このマテリアを使うと何が出力されるか |

キャラクターは前者だけを知り、後者に転送する。

### 10.9 契約（ex03）

| ID | 成功または失敗のあと、真であること |
|----|--------------------------------------|
| CI-30 | 課題の main と同じ手順の出力は、氷の 1 行と治療の 1 行だけ |
| CI-31 | `clone()` の戻り値は別アドレスで、`getType()` は同じ |
| CI-32 | `AMateria&` で Ice に Cure を代入したあと、Ice の type は `"ice"` |
| CI-33 | `createMateria("fire")` は 0。`"Ice"` も 0（小文字だけが一致） |
| CI-34 | 5 個目の `equip` はスロットを変えない。そのポインタは生きていて、呼び出し側が `delete` できる |
| CI-35 | `unequip(0)` のあと `use(0)` は空出力。保存していたポインタは `delete` できる。次の `equip` は空いた 0 番に入る |
| CI-36 | `use(-1)`、`use(4)`、`unequip(-1)` は出力も状態も変えない |
| CI-37 | コピーに代入したあと元を破棄しても、コピーの `use(0)` は氷の文を出す。名前もコピーされている |
| CI-38 | 自己代入のあと、装備は使える |
| CI-39 | `learnMateria(new Ice())` を 5 回したあと、`createMateria("ice")` は非 0。破棄が二重解放しない |
| CI-40 | `MateriaSource` をコピーし、元を破棄したあと、コピーから `"ice"` を作れる |
| CI-41 | `equip(0)` はスロットを埋めない |
| CI-42 | 同じポインタの 2 回目の `equip` は 1 番スロットを埋めない。破棄が一度だけになる |

CI-39 の「リークしない」は、プロセス内の文字列比較だけでは 5 個目の `delete` を直接は見られない。
二重解放が無いことは「破棄して落ちない」ことと、可能ならサニタイザで見る。
参考実装の `learnMateria` は空きが無ければ `delete` する。そのコードと CI-39 を一緒に説明する。

### 10.10 循環させない include

```text
AMateria.hpp     ICharacter を前方宣言するだけ
ICharacter.hpp   AMateria を前方宣言するだけ
Ice.cpp          ICharacter.hpp を include する（getName を呼ぶ）
Character.hpp    ICharacter.hpp と、AMateria の前方宣言
Character.cpp    AMateria.hpp を include する（delete と use と clone に定義が要る）
```

`AMateria.hpp` から `Character.hpp` を include しない。
`ICharacter` と `IMateriaSource` の空の virtual デストラクタは、課題がクラス定義の中に書いている。
この二つだけヘッダに本体がある。自分で足す関数は cpp に置く。

課題が public に置いている `AMateria(std::string const &)` は public のままにする。
`explicit` を付ける。`AMateria("ice")` の直接初期化は通り、`AMateria m = std::string("ice")` のような暗黙変換は通らない。抽象クラスなので外からオブジェクトは作れないが、意図は「文字列はマテリアそのものではない」。

## 12. よくある失格・減点

| 行為 | 結果 |
|------|------|
| `using namespace std;` または `friend` | 課題の一般規則では -42 |
| `std::vector`、`<algorithm>` | 同上 |
| `printf` / `malloc` / `free` / `nullptr` / `override` | 0 点、または C++98 でコンパイルできない |
| ヘッダに関数本体（課題のインターフェースデストラクタ以外） | その演習が 0 点になりうる |
| インクルードガードが無い、ヘッダが単体で include できない | 0 点になりうる |
| 基底ポインタの `delete` でデストラクタが非 virtual | 未定義動作。ex01 の順序テストが落ちる |
| 浅いコピー | 二重解放、または CI-12 / CI-37 が落ちる |
| `Character.cpp` で `"ice"` と `"cure"` を分岐 | 提示 main は動く。10.8 の設計ではなく、評価の修正課題で壊れる |
| ex03 のコンストラクタがメッセージを出す | CI-30 が落ちる |

### 13.1 参考実装を読んで確認すること

コードを開いたら、次の 6 つを指させる。指させなければ、設計を採用したことにならない。

1. `Dog::Dog` の初期化子が `Animal("Dog")` であり、本体に `type = ` が無いこと。
2. `WrongAnimal::makeSound` に `virtual` が無く、デストラクタにはあること。
3. `Dog::operator=` が `*brain_ = *other.brain_` であり、`brain_ = other.brain_` ではないこと。
4. `Animal::makeSound` の宣言が `= 0` なのは ex02 だけであること。
5. `Character::equip` が `clone` を呼ばず、`unequip` が `delete` を呼ばないこと。
6. `Character.cpp` が `Ice.hpp` を include していないこと。
